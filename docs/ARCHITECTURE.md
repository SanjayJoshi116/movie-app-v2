# Architecture: Design Decisions

Detailed rationale behind non-obvious implementation choices across the stack — auth, pagination, responsive layout, recommendations, and more. See the main [README.md](../README.md) for the folder structure, request-flow diagram, and feature list.

- **Auth** — JWT via `djangorestframework-simplejwt`. Access (60 min) + refresh (7 days) tokens stored in `localStorage`. `userApi.ts` intercepts 401s and silently refreshes before retrying failed requests. Password reset uses Django's built-in token generator sent via email; the link encodes a base64 uid and a one-use HMAC token.
- **Refresh-token rotation persistence + late-401 replay** — `SIMPLE_JWT` rotates the refresh token on every refresh and blacklists the old one (`ROTATE_REFRESH_TOKENS` + `BLACKLIST_AFTER_ROTATION`). The `userApi.ts` interceptor used to store only `data.access`, so the second refresh (~2h in) always sent an already-blacklisted refresh token and forced a logout. It now stores `data.refresh` as well. Separately, before starting a refresh it compares the failed request's `Authorization` header with the currently stored access token. If they differ, a refresh has already finished since that request was sent, so the request is replayed with the current token instead of starting a second refresh against the (now blacklisted) refresh token. The existing `isRefreshing` + `failedQueue` still covers 401s that arrive *during* a refresh; the header comparison covers the ones that arrive *after* it.
- **Cross-tab refresh lock + session-unchanged write** — `isRefreshing` is per tab, but all tabs share one `localStorage`. Two tabs waking from sleep with the same expired token used to both submit refresh token R1: the server rotated it for one and rejected the other, whose `forceLogout()` then wiped the winner's freshly stored R2, logging out both. `refreshTokens()` now runs inside `navigator.locks.request("cinedb-token-refresh", …)`. Inside the lock, a tab whose remembered refresh token no longer matches storage skips the network call and adopts the stored access token (another tab already rotated it). The same comparison also runs after a rejected refresh. That covers browsers without Web Locks (jsdom, old browsers), and it's needed even with them: Chromium syncs `localStorage` across tabs asynchronously, so a tab that just acquired the lock can still read the old token for ~20ms (seen live). It then sends one extra refresh, gets `401`, and is rescued here. If storage still shows the old token after a `401`, `rotationArrives()` waits up to 1.5s for a `storage` event carrying the new one before giving up and logging out. The cost is one wasted request in the rare simultaneous case. An IndexedDB handoff would avoid it, but wasn't worth the code. Adoption also requires `cinedb_user`'s id to be unchanged, so a request is never replayed with a different account's token. Separately, a successful refresh is stored only if `cinedb_refresh` still equals the token sent. Otherwise the user logged out (or someone else logged in) while it was in flight, and storing it would silently sign the old session back in. Both "session changed" outcomes reject the request without redirecting (`SessionChangedError`), because local state already reflects what the user did. The refresh POST has a 10s timeout so a hung request can't hold the lock.
- **Revoke-all on credential change** — `password_reset_confirm` and the profile PATCH (when `new_password` is set) call `_revoke_all_refresh_tokens(user)` (`auth_views.py`), which blacklists the user's live (unexpired, not already blacklisted) `OutstandingToken`s in one `bulk_create(ignore_conflicts=True)`. That is 2 queries whatever the token history; the first version looped over every token ever issued with 2 queries each, inside a 30s gunicorn worker. The profile path revokes first, then issues a fresh pair via `_tokens_for_user` and adds `access`/`refresh` to the response (additive), so the session that made the change stays signed in and every other session ends at once. The snapshot alone had a race: a refresh on another device could pass the blacklist check just before the change, then record its rotated token just after the snapshot, and that token survived and kept rotating. So tokens are also **password-bound** (`fix-password-revoke-race`). `SIMPLE_JWT["CHECK_REVOKE_TOKEN"]` stamps a `hash_password` claim (MD5 of the stored password hash) on every token, and rotation and `access_token` copy it forward. `JWTAuthentication` rejects a stale or missing claim on every request, so other sessions' access tokens die immediately instead of at expiry. Stock simplejwt does *not* check the claim on refresh, so `SafeTokenRefreshSerializer._check_password_claim()` does, before rotating. A token minted mid-race carries the old claim and fails at its next use. Turning this on logged out every pre-existing session once, because their tokens had no claim (a hard cutover, chosen over a grace period). The blacklist snapshot stays as defense in depth. This depends on `djangorestframework-simplejwt>=5.5.0`, the first version that records rotated tokens in `OutstandingToken` (older versions would silently miss every token after the first refresh). `OutstandingToken` grows with every sign-in and refresh; simplejwt's `flushexpiredtokens` prunes expired rows (their blacklist rows cascade) at every backend start, bounded and best-effort (`bound-background-load`), so a deploy or restart keeps the table to roughly the live sessions. `POST /api/auth/logout/` is simplejwt's stock `TokenBlacklistView` (`AllowAny`, body `{refresh}`). It returns 401 for malformed/already-blacklisted tokens, never 500.
- **Each tab bound to the account it shows (`fix-session-sync`)** — `AuthProvider` used to read `localStorage` only on mount, while `userApi`'s request interceptor reads `cinedb_access` on every call. So after tab 1 logged out and signed in as B, tab 2 kept rendering A's library but saved its writes to B. Its removes, using A's ids, got 404. There are two layers now. (1) A `storage` listener in `AuthProvider` re-reads the auth keys on any change to `cinedb_user`/`cinedb_access` (or a `clear()`) and compares user ids. Session gone → `sessionStorage.clear()` + signed-out state. Signed-out tab sees a user → adopt it (the hooks fetch on the `isAuthenticated` flip). Same id → adopt the payload (profile edits). Token-only rotations are ignored. A **different** id → clear `sessionStorage` and `window.location.reload()`. Every library hook refetches only when `isAuthenticated` flips, so an A→B swap would refetch nothing. Remounting `AuthProvider`'s children wouldn't reset `BrowserRouter` (it sits outside), its history state, or module-level state in `userApi`. (2) `bindSessionUser(id)` (`userApi.ts`) records which account the tab shows, and `AuthProvider` calls it on every user change. The request interceptor refuses (`SessionChangedError`, nothing sent) while the stored user id differs. That closes the gap before the storage event lands, which Chromium delivers asynchronously. A click in a background tab can run first.
- **Only a rejected refresh ends the session; refresh/logout have their own throttle (`fix-session-sync`)** — simplejwt's refresh and blacklist views set `authentication_classes=()`, so they fell under the default `anon: 300/day` per-IP throttle. Each device refreshes ~24×/day, so about a dozen users behind one NAT ran it dry. The interceptor then called `forceLogout()` on *any* refresh error, so a 429 logged everyone out. Now `TokenSessionThrottle` (`AnonRateThrottle`, scope `token_refresh`, 60/min) is the *only* throttle on both views. It's anon-based because nobody is authenticated there, so the key is the IP either way. The client forces a logout only on a `400`/`401` from the refresh endpoint (`isRejectedRefresh`). A 429, 5xx, timeout or network error rejects the waiting requests (they show `LoadError`/error toasts) and keeps the tokens, so the next `401` refreshes again.
- **Password rehash vs. the password-bound claim** — Django re-saves a password hash when the hasher's parameters differ (e.g. hashes made under Django 6.0's PBKDF2 iteration count, now running on 5.2). That changes `CHECK_REVOKE_TOKEN`'s `hash_password` claim, so every token minted under the old hash dies. In the profile PATCH, verifying `current_password` (an email change) can trigger it. `profile` snapshots the claim before the serializer validates and returns a fresh pair if it changed, so the session making the edit stays signed in. Nothing is revoked, because the password itself didn't change. **Accepted:** a *login* that rehashes ends the user's *other* sessions once per hasher upgrade. The device logging in gets fresh tokens anyway. Preventing it would need a permanent custom hasher that ignores iteration downgrades, which isn't worth it for a one-time effect.
- **Superseded responses are dropped, not aborted (`surface-failures-2`)**: `CalendarPage` numbers each fetch (`requestIdRef`) and lets only the latest set `groups`/`loading`/`loadFailed`. Its "All" filter fetches movies then TV, so it used to finish after a later "TV Shows" pick and overwrite it. `HeroBanner` and FollowingPage's recommendations use a `cancelled` flag in the effect cleanup. `AbortController` was skipped because `api/tmdb.ts` callers take no signal, and threading one through the paging loops buys nothing visible: the stale request just completes and is ignored.
- **The search term is in the URL (`surface-failures-2`)**: `SearchBox` navigates to `/search?q=<term>` and keeps `tab` when already on `/search`. `SearchPage` reads `q` in a layout effect (before the tabs' first fetch effects) and pushes it into `AppContext.searchTerm`, which stays the live value for the sidebar box, Home's filter and the per-query caches. A reload, a shared link or a login round trip (`postLoginPath` keeps the query string) therefore shows the same search and tab. Making the URL the only store would have touched every `searchTerm` reader for no extra user-visible gain.
- **`clearSession()` as the single client teardown** — `userApi.ts` exports `clearSession()`, which removes `cinedb_access`/`cinedb_refresh`/`cinedb_user`/`cinedb_recent_searches` and calls `sessionStorage.clear()`, keeping device prefs (`cinedb_theme`, `cinedb_sidebar_collapsed`). Both explicit logout (`AuthContext.logout()`: best-effort `logoutSession()` via `publicApi` with a 5s timeout, not awaited → `clearSession()` → `setUser(null)`) and the interceptor's forced-logout branch go through it, so nothing from one account (cached recommendations, search results, list filters, recent searches) leaks to the next account signing in on the same tab. `sessionStorage.clear()` is used instead of a key allow-list because every key the app writes there is account- or session-derived, and an allow-list would rot as new caches are added. `useRecentSearches` also resets its in-memory state when `user` becomes `null`, because `SearchBox` is always mounted. Don't add another inline key-removal block; extend `clearSession()`. Pages that save a cache in an unmount cleanup (`RecommendationsPage`, `SearchPage`) write through `saveSessionCache()`, which is a no-op once `cinedb_access` is gone. Logout unmounts the page *after* `clearSession()` runs, so a plain `sessionStorage.setItem` there wrote the previous user's recommendations straight back. The next user then got them from cache (and never fetched their own) for up to 5 minutes.
- **Retry-on-500 only for safe methods** — the interceptor's one-shot 500 retry is gated on `RETRYABLE_METHODS` (`get`/`head`/`options`). A write that succeeded server-side but returned 500 used to be re-sent blindly (e.g. a duplicate list on create). Writes now surface the 500 to the caller.
- **Password strength** — Registration, profile password change, and password-reset confirmation all run Django's configured `AUTH_PASSWORD_VALIDATORS` (`validate_password()`) — minimum length 8, rejects common passwords, rejects passwords too similar to the username/email, rejects all-numeric passwords.
- **Account deletion** — `DELETE /api/auth/delete-account/` requires the user's current password in the request body and re-verifies it with `check_password()` before deleting; the frontend's Danger Zone in `ProfileModal` collects it inline, isolated on its own tab.
- **Avatar upload** — `POST/DELETE /api/auth/avatar/` (separate from the JSON-only profile PATCH) stores a photo on a new `Profile` model (`OneToOneField` to `User`, `ImageField`, versioned `avatars/user_<id>_<ms>.<ext>` path, see "Avatar versioning and cleanup"). Validates size (5MB max) and decodes the upload with PIL: the stored extension comes from the decoded `Image.format` (`JPEG`/`PNG`/`WEBP` → `jpg`/`png`/`webp`), never the client's filename or declared content type, and any other format is rejected. Since `/media/` is served with a content type guessed from the extension, a PNG/HTML polyglot named `x.html` used to be served as `text/html` on the app's own origin (stored XSS); `avatar_upload_path` also refuses non-whitelisted extensions as defense in depth, and migration `0018` renamed or removed any legacy avatar stored with an unsafe extension; deletes the previous file (on commit) on replace, removal or account deletion so nothing orphans. `UserSerializer.avatar_url` is relative (not `build_absolute_uri()`), because the frontend can reach Django under different hosts (the dev server, a LAN IP, nginx in Docker), so an absolute URL built from one request's `Host` can be wrong for another client. The frontend resolves it against its own base via `resolveAvatarUrl()`/`REACT_APP_MEDIA_BASE_URL`. Media is served by Django directly (`re_path` + `django.views.static.serve`, unconditional — no CDN in this stack), reached directly on port 8000 in dev and reverse-proxied at `/media/` by `nginx.conf` in Docker (a dedicated `location` straight to the `backend` service).
- **Responsive breakpoints** — Three CSS-only tiers reusing antd's own scale, no JS width checks anywhere: `<768px` (phone, `Sidebar` hidden/`BottomNav` shown, unchanged), `768-991px` (tablet, new — `Sidebar` collapses to a 64px icon-only rail via a `@media` block in `App.css` that hides `.ant-menu-title-content`/username text/logo text and shows a compact "C" glyph instead), `≥992px` (desktop, full 220px sidebar, the unqualified default rule). `src/index.css` adds a root `overflow-x: hidden; max-width: 100vw` guard, and list-page filter-bar `Input`/`Select` widths (previously rigid `width: N`) are now `width: "100%", maxWidth: N` so they shrink on narrow phones instead of forcing horizontal scroll. Auth pages' `Card` is `width: "100%", maxWidth: 360` (was a fixed 360) so it doesn't overflow under-360px viewports. `playwright.config.ts` adds a `mobile-chrome` (Pixel 5) project so the existing E2E suite also runs at phone width; `e2e/responsive.spec.ts` asserts sidebar/bottom-nav behavior at all three tiers plus no-overflow at 320px/340px.
- **Login/register use the unauthenticated API client** — `AuthContext.login`/`register` call `publicApi` (no response interceptor), not the default `userApi`. `userApi`'s 401-refresh interceptor previously intercepted a failed login's 401, found no refresh token yet, and hard-redirected to `/login` before the page's own `catch` could show an "Invalid username or password" message — so bad credentials failed silently.
- **List pagination** — `/api/watchlist/`, `/api/watched/`, `/api/ratings/`, and `/api/followed-people/` are paginated (`DefaultPagination`, page_size=100) and return `{count, next, previous, results}`. `src/utils/fetchAllPages.ts` transparently walks all pages so the frontend hooks (`useWatchlist`, `useWatched`, `useRatings`, `useFollowedPeople`) still expose the full list — it also accepts a plain array response for back-compat with mocked tests. `DefaultPagination.get_next_link`/`get_previous_link` return the next/previous page number rather than DRF's default absolute URL (`request.build_absolute_uri()`), since building that URL validates the request's Host header against `ALLOWED_HOSTS` and 500s (`DisallowedHost`) for any host besides bare `localhost` and its loopback address under `DEBUG=True` — `fetchAllPages.ts` only ever checked `next` for truthiness, so returning a page number instead is a drop-in fix with no frontend change needed. Every paginated list orders by its timestamp **plus an `-id` tiebreaker**. A bulk import gives many rows the same timestamp (Windows clock resolution yielded 16 distinct values across 1,200 rows), and ordering by a non-unique key made `fetchAllPages` return duplicates and skip rows.
- **Sticky sidebar / `overflow-x` scoping** — `.app-sidebar` (`App.css`) is `position: sticky; top: 0`, which sticks relative to the *nearest ancestor with a scrolling mechanism* — not necessarily the viewport. `src/index.css` scopes `overflow-x: hidden` to `html` only (not `body`/`#root`) because setting `overflow-x` without an explicit `overflow-y` silently promotes `overflow-y` to `auto` too (per the CSS overflow spec), which would turn `body`/`#root` into unintended scroll containers sitting between the sidebar and the true viewport scroller — since those containers' own `scrollTop` never moves, the sidebar's sticky offset would never engage and it'd just scroll away with the page. Don't add `overflow-x: hidden` (or any non-`visible` overflow value) to `body`/`#root`/any ancestor of a `position: sticky` element without also handling `overflow-y` explicitly.
- **Popup positioning inside a sticky container** — `SearchBox.tsx`'s recent-searches `Dropdown` sets `getPopupContainer` to mount its popup inside the sidebar's own search wrapper (`Sidebar.tsx`, `position: relative`) instead of antd's default `document.body`. A popup mounted in `body` repositions itself via scroll-linked recalculation built for a trigger that scrolls with the page; once its trigger lives inside a genuinely `position: sticky` (viewport-pinned) ancestor, that recalculation visibly glitches for a frame on every scroll tick. Any future dropdown/popover/tooltip anchored to something inside the sidebar should set `getPopupContainer` the same way rather than defaulting to `body`.
- **Recommendations/Similar genre filtering** — `filterByGenreOverlap()` (`src/utils/filterByGenreOverlap.ts`) keeps only items sharing ≥half the opened title's genre count, falling back to the unfiltered list if that would empty the section. Applied to both "Similar" and "Recommendations" on `MovieDetails.tsx`/`TVShowDetails.tsx` — TMDB's own recommendations/similar endpoints return `genre_ids` on every item, so no extra API call is needed.
- **Rate limiting** — DRF `AnonRateThrottle` subclasses applied to public auth endpoints: login (10/min), register (5/min), password reset request + confirm (5/hour, same scope for both halves of the flow). Rates configured in `REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]` in `settings.py`; no extra package needed.
- **JWT refresh hardening** — `ROTATE_REFRESH_TOKENS` is paired with `BLACKLIST_AFTER_ROTATION` (`rest_framework_simplejwt.token_blacklist` in `INSTALLED_APPS`), so a rotated-out refresh token is actually invalidated instead of staying valid for its full remaining lifetime. `POST /auth/token/refresh/` uses a custom `SafeTokenRefreshView`/`SafeTokenRefreshSerializer` (`auth_views.py`) instead of the stock simplejwt view — the stock `TokenRefreshSerializer.validate()` does an unguarded `User.objects.get(...)`, which 500s instead of cleanly 401ing if the token's user no longer exists (e.g. a deleted account replaying an old stored token).
- **Production config** — `DEBUG`, `ALLOWED_HOSTS`, and `SECRET_KEY` are all env-controlled in `backend/cinedb/settings.py`. `ALLOWED_HOSTS` fails closed (empty by default) rather than defaulting to `*`. When `DEBUG=False`, an unset `SECRET_KEY` raises `ImproperlyConfigured` at startup instead of a silent fallback, and so does a missing or non-`http(s)` `FRONTEND_URL` (`tidy-app-config`): it is the base of password-reset links, and its old `localhost:3000` default mailed production users dead links. It deliberately isn't derived from the request's `Host`, which a client controls (reset-link poisoning). Its trailing slash is stripped in every mode. `CORS_ALLOW_ALL_ORIGINS` is only enabled in `DEBUG`; production reads explicit origins from `CORS_ALLOWED_ORIGINS`.
- **Backend view split** — `views.py` was a 750-line monolith; now a thin re-export barrel. Domain logic lives in `auth_views.py`, `watchlist_views.py`, `watched_views.py`, `ratings_views.py`, `lists_views.py`, `tmdb_views.py`, `stats_views.py`, `social_views.py`. `urls.py` is unchanged.
- **Bulk import endpoints** — `POST /api/watched/bulk/`, `/api/watchlist/bulk/` and `/api/ratings/bulk/` all go through `bulk_import()` (`backend/userdata/bulk_import.py`). It caps a request at 500 entries and validates every entry before writing anything, all-or-nothing: a malformed entry rejects the batch with `400 {"entries": {"<index>": ...}}`. Entries with no `mediaId` are skipped, a `null` `voteAverage` is stored as `0`, and each entry may carry its own `mediaType` (overriding the request default). It dedupes on the validated `(int id, type)`, then runs the existing-pairs pre-check and a `bulk_create(ignore_conflicts=True)` in one transaction. The endpoints are **create-only**: an existing entry is skipped, never updated, and `{added, skipped}` comes from that pre-check. Supplied `watchedAt`/`addedAt`/`ratedAt` are kept (future ones are rejected), which is why those model fields are `default=timezone.now` rather than `auto_now_add`, which would overwrite them. Single-item serializers keep them `read_only`. `bulk_create` sends no `post_save`, so the watched endpoint calls `signals.schedule_refresh()` once itself when it added anything. The ratings endpoint never pushes to TMDB: a restore shouldn't fire hundreds of third-party writes. The frontend's `bulkImport()` (`userApi.ts`) sends chunks sequentially and counts a rejected chunk as failed. A chunk ends at 500 entries or at `BULK_MAX_BYTES` (2,000,000 UTF-8 bytes of JSON), whichever comes first (`tidy-app-config`): Django refuses bodies over `DATA_UPLOAD_MAX_MEMORY_SIZE` (its 2.5 MB default, deliberately not raised, since it bounds per-request memory), and 500 ratings with 5,000-character emoji or CJK reviews reach ~10 MB, past nginx's 8 MB too. A single entry is never split.
- **List items import in bulk too (`fix-stats-math`)** — A backup restore and the per-list CSV import used to add items one `POST` each (20 in parallel), and `UserListItem.added_at`/`UserList.created_at` were `auto_now_add`. Restored items got restore-time dates in a scrambled newest-first order, and a few thousand items could use up the `5000/day` user throttle for the whole app. `POST /api/lists/<id>/items/bulk/` now goes through the same `bulk_import()`, so there is no second bulk mechanism. Its only addition is a `scope` kwarg: the existing-pairs pre-check filters on `{"user_list": list}` rather than the default `{"user": request.user}`, because list items aren't keyed by user. Someone else's list is a 404. Both list timestamps are `default=timezone.now`, list create accepts an optional past `createdAt` (ignored on update, so a rename can't move a list), and the backup manifest carries each list's `createdAt` (additive; older backups still import). The client helper `bulkAddListItems()` chunks at 500 like `bulkImport()`. Rows without a date (hand-made CSVs, lists from older backups) are sent in **reverse** file order. They all get the import instant, so the `-added_at, -id` ordering falls back to `-id` and shows them in file order. Dated rows are ordered by their dates, so the reversal doesn't affect them.
- **Backup format v2** — `src/utils/backup.ts` builds and reads the "Export All" ZIP. v2 is purely additive over v1 (`watchlist.csv`, `watched.csv`, `lists/*.csv`): a `manifest.json` (`format: "cinedb-backup"`, `version`, and every list, empty ones included, with its original name, description and a collision-safe file name), a `ratings.csv`, and `runtime_minutes`/`platform` appended to `watched.csv`. Without a manifest the reader falls back to v1 rules (list name from the file name); unknown files and columns are ignored either way, so old backups import here and old app versions can import new backups. All CSV reading goes through one RFC 4180 parser (`parseCSV` in `csvParse.ts`): quoted delimiters and newlines, CRLF, BOM, and `,`/`;`/tab detected from the header. Reviews contain newlines, so a per-line split would corrupt them. Import All runs each section in its own try/catch and shows per-section added/skipped/failed counts. It matches lists by exact name against a fresh `/lists/` read, so re-running an import is idempotent.
- **Input validation: bad input is a 400, never a 500** — The API's camelCase fields are hand-declared in `serializers.py` (`mediaId = IntegerField(source="media_id")`), and hand-declaring a field drops everything DRF would have derived from the model: `max_length`, `choices`, integer bounds. So each hand-declared field restates its column's limits: `max_length` matching the model, ids bounded to `1..INT32_MAX` (Postgres `integer`), and `mediaType` as a `ChoiceField(MEDIA_TYPES)` via the shared `MediaIdentityMixin`. That mixin also rejects (rather than silently ignores) a PATCH that changes `mediaId`/`mediaType`, which would otherwise collide with `unique_together`. Every float input uses `FiniteFloatField`: plain `FloatField` accepts the string `"NaN"` (min/max comparisons with NaN are always false), Postgres stores it, and DRF's strict JSON renderer then 500s every later read of that account's data, permanently. Endpoints that used to read `request.data.get(...)` directly now go through small type/shape-only input serializers (`LoginInputSerializer` etc.). A JSON array body or a non-string field gets a `400` instead of an `AttributeError`, while each view keeps its own "required" checks and messages, so well-formed requests behave exactly as before.
- **Avatar decode failures** — `avatar` catches `DecompressionBombError` (not an `OSError`), plus the `SyntaxError`/`ValueError`/`IndexError` that Pillow plugins raise on malformed files during `verify()`. `IndexError` comes from a PNG with no `IDAT` chunk, found by the fuzz cases in `test_input_validation.py`. It also explicitly rejects `width*height > Image.MAX_IMAGE_PIXELS`: between 1× and 2× that limit Pillow only warns. This is an explicit check rather than `warnings.catch_warnings()`, because that mutates process-global state and isn't thread-safe under the threaded dev server.
- **Production server** — The backend container runs `docker-entrypoint.sh` (`migrate --noinput` → `createcachetable` → time-boxed warm-up → `gunicorn cinedb.wsgi:application`) instead of Django's dev server. `makemigrations` is no longer run automatically at container boot — generate new migrations explicitly with `python backend/manage.py makemigrations userdata` during development, same as any other Django project. `backend/start.py` (used by `npm run dev` for local non-Docker dev) keeps the DB-create-if-missing + `migrate` + `runserver` flow, minus `makemigrations`.
- **DB indexes** — Migration `0008_add_indexes.py` adds compound indexes on `(user, *_at)` fields across WatchedEntry, WatchlistEntry, RatingEntry, FollowedPerson, EpisodeProgress, and `(user, release_year)` for stats decade queries.
- **Split contexts** — `AppContext` used to be one context bundling search/filters/theme with watchlist/watched/ratings, so any UI-state change (typing in search, toggling a genre) re-rendered every consumer, including movie/TV cards. It's now `UIContext` + `WatchlistContext` + `WatchedContext` + `RatingsContext`, each independently memoized; `useAppContext()` is kept as a back-compat shim so existing call sites are unchanged. `Movie`, `TVShowCard`, `RecCard`, and `CreditCard` are wrapped in `React.memo` and read only the specific contexts they need.
- **Stable hook callbacks** — `useWatchlist`, `useRatings`, and `useWatched` use `useCallback` with a ref pattern (`watchlistRef.current = watchlist`) so returned functions only change identity when `isAuthenticated` changes, not on every render. This keeps the split contexts' `useMemo` from recomputing on unrelated parent re-renders.
- **API key security** — The TMDB key lives in `.env` and is only read by Django (`tmdb_proxy`). Frontend requests go through `/api/tmdb/*`.
- **Backend data** — All user data lives in PostgreSQL, bound to the authenticated user. No localStorage drift.
- **Recommendations** — K-means clustering on rating-weighted genre vectors of the user's watch history (scikit-learn). Followed-people recommendations are fetched in parallel with personal recommendations and shown at the top. Only fetched once on first load (guarded by a `useRef` flag). Results are pre-computed and stored in `UserRecommendationCache` (PostgreSQL) at backend startup via the `compute_recommendations` management command; endpoints serve from DB in ~1ms. Stale cache (>12 h) triggers a background thread refresh on the next request. The `for-you`/`personalized` endpoints report `{status: "pending" | "ready", sections}` — an in-process set tracks which users have a refresh in flight so concurrent requests don't spawn duplicate threads. While `pending`, `RecommendationsPage` polls every 3s (up to ~1 min) instead of showing a terminal empty state.
- **TMDB key never reaches clients or logs** — The v3 API authenticates with an `?api_key=` query param, and `requests.HTTPError` messages embed the full URL, so `str(e)` is a credential. TMDB-auth views (`tmdb_views.py`) return a fixed `"Couldn't reach TMDB. Try again."` 502 instead of echoing the exception (any signed-in user could previously read the server key off a failed create-session call). For logs, `userdata/logging.py`'s `RedactingFormatter` is the console handler's formatter in `settings.LOGGING`: it replaces the `TMDB_API_KEY` value with `***` in the fully formatted record, tracebacks included. One handler-level guard instead of per-call-site redaction, because there are already 5+ `logger.exception`/`warning("%s", e)` sites and a new one would silently reintroduce the leak. That handler is on the **root** logger, not just `userdata` (`harden-logging`). urllib3 logs every retried request's URL, `api_key` included, at WARNING (`tmdb_proxy`'s `Retry` session triggers it). With only `userdata` wired, that line reached stderr through Python's last-resort handler unredacted, which put the key in `docker logs`. The project config also overrides `django` to propagate to root with no handlers of its own. Django's defaults are a debug-only console handler plus `mail_admins` (no `ADMINS` set), so production 500s used to log nothing at all. `django.request` is set to ERROR, so unhandled 500s log a traceback and routine 4xx (401 refresh churn, 404s) stay quiet. Any new handler must use the `redacting` formatter (`test_logging.py` checks it). The caller-supplied `redirect_to` is `urlencode`d into the TMDB authorize URL so it can't inject extra query params.
- **Throttle identity and shared counters** — `REST_FRAMEWORK["NUM_PROXIES"]` comes from `TRUSTED_PROXY_COUNT` (default `0` = ignore `X-Forwarded-For`, use `REMOTE_ADDR`; `docker-compose.yml` sets `1` for nginx, which appends the real address last via `$proxy_add_x_forwarded_for`). Unset, DRF keyed throttles on the *whole* client-supplied XFF string, so rotating a made-up header minted a fresh bucket per request. Hardcoding `1` would recreate that bypass under `npm run dev`, where there's no proxy and the rightmost entry is client-controlled. With `DEBUG` off, `CACHES` is a `DatabaseCache` (`cinedb_cache`, created by `createcachetable` in `docker-entrypoint.sh`/`start.py`) so gunicorn's 3 workers share one counter; per-process LocMem effectively tripled every limit. Redis was rejected for now: a new service + dependency for a cache whose only consumer is throttling. The table is sized with `MAX_ENTRIES: 50_000` (`PRODUCTION_CACHE` in `settings.py`). `DatabaseCache`'s default of 300 culls a third of all keys once exceeded (after dropping expired ones), so with a few hundred active clients live throttle counters were reset early. There's one key per client per throttle scope.
- **TMDB proxy time budget** — `tmdb_proxy_views.py` keeps connect retries (the transient-reset case its shared `Session` exists for) but caps read retries and timeouts: `timeout=(3.05, 6)`, `Retry(total=2, connect=2, read=1, backoff_factor=0.5)`, worst case ~22s. The earlier `timeout=20` × 5 attempts could hold a gunicorn sync worker ~100s, past gunicorn's 30s `--timeout`. The worker was then killed, the browser got a bare nginx 502, and the other 2 workers absorbed every other request. That bound was first computed from urllib3's retry/backoff semantics (`WORST_CASE_SECONDS`, ~22s), but urllib3 tries the connect once per address `getaddrinfo` returns, and `api.tmdb.org` has four, so the real worst case was ~37s. Since `bound-tmdb-calls` the whole call runs under a wall-clock deadline instead (`PROXY_DEADLINE_SECONDS`, via `tmdb_client.call_with_deadline`), and `test_tmdb_proxy` pins that deadline 5s under the `--timeout` parsed from `docker-entrypoint.sh`. A test drives the real urllib3 connect loop over four fake addresses to prove it.
- **Request-path TMDB calls run under a deadline on a bounded pool** (`bound-tmdb-calls`) — `call_with_deadline` submits the call to an 8-thread pool and waits with a timeout. An overrun raises `TMDBDeadlineExceeded`, a `requests.Timeout`, so existing handlers treat it as a failed TMDB call. The abandoned thread finishes on its own timeouts and touches only the network, so leaving it is safe. When the pool is full during an outage, new calls fail at their deadline. Each endpoint's budget is calls × deadline, pinned under gunicorn's timeout. Alternatives rejected: modelling per-address connects (depends on DNS), forcing a single address (loses failover), `signal.alarm` (main thread only, clashes with gunicorn's signals).
- **TMDB session revokes run after the local change, in the background** — Reconnect stores the new session before revoking the old one. Disconnect clears the session first, and account deletion deletes first. The revoke then runs on commit in a daemon thread. A worker killed mid-request used to leave a revoked session stored (every later rating sync failed) or an account undeleted. Ordering between revokes doesn't matter, so the background is safe there.
- **Rating sync stays in the request, bounded** — It runs after the local save, under `TMDB_CALL_DEADLINE`. Moving it to the background would make saves instant, but two gunicorn processes could deliver a rate and a delete to TMDB in either order. Making that safe needs a DB read of the latest state in the background thread, which the worker-thread rule forbids. In the request, each response comes after its sync, and the frontend sends one write per title at a time.
- **Email change requires re-auth** — `UserProfileUpdateSerializer` requires and checks `current_password` when the submitted email differs case-insensitively from the current one, enforces case-insensitive uniqueness (skipped on an unchanged resubmit so legacy duplicate-email accounts can still save), and the `profile` view emails the *old* address after a change (best-effort, same broad-except rationale as the reset email). Without it, a stolen access token could change the email and then use password reset for a full takeover. `ProfileModal.tsx` keeps `current_password` in the payload only when the email or username actually changed, since the form always resubmits both. The username got the same gate later (`harden-account-input-2`): sign-in is by username, so a rename with only an access token locked the owner out; the address on file is told of a rename. New passwords are also checked by `UserAttributeSimilarityValidator` against the account's (pending) username, email and names, at Django's default 0.7 threshold, which still accepts a doubled username like `alicealice` (0.67) but not `alice2024` (0.71). Reset links expire after `PASSWORD_RESET_TIMEOUT = 3600` (Django's default is 3 days), and the reset email builds its "expires in" sentence from that setting so the two can't drift.
- **Fail-closed settings** — `DEBUG` defaults to off; with it off, `settings.py` refuses an empty/wildcard `ALLOWED_HOSTS` or the built-in dev `SECRET_KEY`. Local dev keeps working without anyone editing their untracked `.env`: `start.py` does `os.environ.setdefault("DEBUG", "True")` (after `load_dotenv`, so an explicit `.env` value still wins), and pytest gets the same default from `backend/pytest_dev_env.py`, loaded as an early `-p` plugin since pytest-django imports settings before a root `conftest.py` runs.
- **Recommendation refresh coalescing** — Every refresh trigger (stale-cache view hits and `WatchedEntry` create/delete signals) goes through one `request_refresh(user_id, *, rerun_if_running)` in `recommendations.py`. Under `_computing_lock`, `_computing_users` holds users with a refresh in flight and `_rerun_users` holds in-flight users that got another trigger. When a run finishes, it either hands off to exactly one follow-up run or frees the slot. Signals pass `rerun_if_running=True` because the data changed and the in-flight result is stale. Views pass `False` because a TTL refresh doesn't need a second pass. Before this, each deleted row started its own raw thread, so `QuerySet.delete()` (which sends `post_delete` per row) on a 500-item "clear watched" started 500 concurrent TMDB-heavy threads. Now it's at most 2 runs per user per worker process. The guard is still in-process only, so the 3 gunicorn workers can each run one. The *status* the endpoints report is cross-process, though: see `refreshing_since` below. Signals schedule via `transaction.on_commit` with `instance.user_id`, so a refresh never reads pre-commit or rolled-back state, and a bulk delete doesn't run one `User` query per row. The thread loads the user by id and exits quietly if they're gone. `post_delete` returns early when `origin` is a `User` instance, so account-deletion cascades don't schedule refreshes for a user who no longer exists.
- **Backup v3 and paced import lookups (`fix-import-export-2`)** — v3 adds `followed.csv` and `episode_progress.csv`. Export reads both at click time (`/followed-people/`, `/episode-progress/`) instead of from a context: `FollowedPeopleProvider` is lazy on purpose, and progress has no context. Either read failing blocks the file, the same as a failed library part. Restores go through the create-only bulk endpoints, so existing progress is never overwritten. `FollowedPerson.followed_at` became settable (migration 0024) so the Following order survives. `bulk_import()` counts `added` from `INSERT … ON CONFLICT DO NOTHING RETURNING 1`. `bulk_create(ignore_conflicts=True)` can't say which rows it skipped, so a row a concurrent request created between the pre-check and the insert used to be counted as added. Poster lookups during imports used to fire 20 at a time, ran into the 120/min `tmdb_proxy` throttle, and silently saved about 40% of a 300-row import without posters. They now share one browser-side schedule (`pacedLookup`, 90/min, 4 in flight), wait out a 429 for its `Retry-After`, treat a 404 as final, and report rows still missing a poster. Server-side filling was the declined alternative. Backup lists match an existing list only if it existed before the import, preferring the same creation time, so same-name lists stay separate and a re-import maps each onto its own copy.
- **Genre families (`fix-recs-correctness`)** — TMDB genre ids are per media type: movies have Action (28) and Adventure (12), TV only Action & Adventure (10759), and Sci-Fi/Fantasy and War work the same way. Recommendations and Stats used to pool raw ids. A taste split across both types was counted as two genres, a movie id went to `/discover/tv`, and a KMeans cluster like `[28, 10759]` was sent as `with_genres=28,10759` (comma means AND), matched nothing, and the section vanished. `genre_families.py` maps every id to a family, and counts, the KMeans vocabulary and Stats charts use families. Every discover call converts back to that type's own ids. One family is OR-ed (`28|12`). Several families AND their primary ids (`28,18`), because TMDB doesn't document mixing `|` and `,` in one value. A type without an id for some family isn't queried, so Horror never goes to TV. The table is static, like `STATIC_GENRE_NAMES`, because TMDB's genre ids are stable. An unknown id becomes its own family for the type it came from, which degrades to the old behavior instead of failing. Merged families show TMDB's TV name ("Action & Adventure").
- **For You "complete" means answered (`fix-recs-correctness`)** — The saved snapshot's `complete` flag used to be derived from "not loading and no computing flag set". A cache-hit mount starts with neither, so leaving it before anything answered saved `complete: true`, and a poll that ran out of attempts cleared its flag the same way. Each polled group now has a state (`pending`/`ready`/`gaveUp`) set only from responses, and only a complete snapshot starts `ready`. `gaveUp` shows a Retry notice. The fetch effect depends on "has any watched title", not the count, so marking a card watched doesn't refetch and reshuffle the groups.
- **Health endpoint is unthrottled, warm-up is time-boxed** — `health` has `@throttle_classes([])`. Without it, the endpoint fell under the default `anon: 300/day` throttle while docker-compose polls it every 10s, so the container went unhealthy after ~50 minutes. `docker-entrypoint.sh` wraps `compute_recommendations` in `timeout 30 ... || echo ...`, the same 30s cap `start.py` uses, so a hung TMDB call can't stop gunicorn from starting.
- **Adult content toggle** — Single switch, in `FilterPanel.tsx`, bound directly to the shared `includeAdult` UI-context value used by every search/discover call. Previously `SearchBox.tsx` also rendered its own copy backed by the same context while `FilterPanel.tsx` kept an unsynced local copy scoped only to discover params — the two could disagree. Consolidated to one control, one value. Since `honest-states-a11y` it is also part of the drawer's draft: Apply writes it with the filters and genres in one handler, so the grid fetches once. Switching it used to refetch on its own, outside the draft every other control follows. The drawer's fields are labelled with `Form.Item htmlFor` + the control's `id`, not `name`: a `name` would hand the values to antd's `Form`, while the drawer keeps its own draft state.
- **Filter params by media type** — `filtersToTMDBParams(filters, sortBy, mediaType)` uses `first_air_date` for TV and `primary_release_date` for movies, and remaps `primary_release_date.*` sort options to `first_air_date.*` for TV discover queries.
- **Episode progress bounds** — The tracker reads `number_of_seasons` and `seasons[].episode_count` from the TMDB TV detail response to cap the +/- controls; no extra API call needed.
- **CSV import** — Parses CSV in the browser (handles quoted fields and `""` escaped quotes), enriches with TMDB poster data in batches of 20, bulk-saves via `/api/watched/bulk/`, then calls `reloadWatched()` so the watched list in context updates immediately.
- **CSV export** — Pure browser-side: `Blob` + `URL.createObjectURL`. No server round-trip.
- **Image lazy loading** — All off-screen/below-fold `<img>` tags carry `loading="lazy"`. Hero backdrop and main detail-page poster intentionally omitted (LCP images; eager is correct).
- **Security headers** — `nginx.conf` sets `X-Frame-Options`, `X-Content-Type-Options`, `X-XSS-Protection: 0`, `Referrer-Policy`, `Permissions-Policy`, `Content-Security-Policy` and (conditionally) `Strict-Transport-Security` at server level, so every response inherits them, including proxied `/api/` and `/media/`. They live in nginx, not Django: nginx serves `index.html` and the static bundle, which are the documents CSP actually protects, and Django only ever returns JSON or media (`django-csp` would miss the SPA document entirely). The CSP allows only what the app loads (self, `image.tmdb.org`, Google Fonts, `youtube-nocookie.com` frames) with `style-src 'unsafe-inline'` for antd's runtime CSS-in-JS; `script-src 'self'` needs no inline exception because `Dockerfile.frontend` sets `INLINE_RUNTIME_CHUNK=false`. It's enforced rather than report-only, since nobody would watch a report endpoint. `X-XSS-Protection` is `0` (the old `1; mode=block` filter is gone from browsers and was abusable where it existed). HSTS is keyed on `X-Forwarded-Proto` through an nginx `map`: the stack doesn't terminate TLS, so it's sent only when the outer terminator reports `https`, and an empty value makes nginx skip the header on plain-HTTP LAN deployments. A forged `X-Forwarded-Proto` over plain HTTP is harmless, since browsers ignore STS received insecurely. An env-templated nginx config was rejected because the only clean way to feed it would be `env_file: .env.docker`, exposing backend secrets to the nginx container.
- **Non-root backend container** — The backend image runs as an unprivileged `app` user (uid 10001). `/app` stays root-owned and read-only to it, with `PYTHONDONTWRITEBYTECODE=1` so Python doesn't try to write `__pycache__`; only `/app/media` (the `media_data` volume) is writable. A fresh named volume inherits that ownership from the image, but a volume created by the old root container stays root-owned, so upgrades need a one-time `chown` (README). Starting as root and dropping privileges in the entrypoint was rejected: PID 1 would run as root on every boot to cover a one-time upgrade case.
- **Image-only migrations, no syncdb** — The backend applies only the migrations baked into its image (`migrate --noinput`). The old `./backend/userdata/migrations` bind mount let a host checkout silently change a running image's schema, and with `USER app` it would be unwritable anyway. `--run-syncdb` only creates tables for apps *without* migrations; every app here has them, so all it could do was hide a missing migration. `backend/.dockerignore` excludes `media/` (and `staticfiles/`, caches), so nobody's local avatars end up in an image.
- **JSON-only production API** — With `DEBUG` off, `REST_FRAMEWORK["DEFAULT_RENDERER_CLASSES"]` is just `JSONRenderer`: the browsable API's pages reference `/static/` assets nothing serves in production (nginx sends `/static/` to the SPA, and there's no admin). A browser opening an API URL gets JSON; a client that accepts *only* `text/html` gets DRF's standard 406, also as JSON. `STATIC_ROOT` is set so `collectstatic` works, but it's never run in the image and whitenoise isn't added, because there's nothing to serve. The Django admin was removed outright in `tidy-app-config` (route and `django.contrib.admin`): no model was registered with it, production never routed it, and in dev it was an unthrottled password form. Accounts are managed through the API and `manage.py` (`createsuperuser`, `changepassword`). Databases created before then keep an unused `django_admin_log` table, which can be dropped by hand.
- **Protected routes** — Unauthenticated access to any non-public path redirects to `/login` with `state.from` preserved, handled inline in `AppInner` (`App.tsx`). Public paths: `/login`, `/register`, `/forgot-password`, `/reset-password/*`. The reverse also holds: a signed-in user on `/login`, `/register` or `/forgot-password` is `<Navigate replace>`d to `postLoginPath(location.state)` (`src/utils/postLoginPath.ts`), the same target `LoginPage` uses after sign-in, so the `from` rule (path + search + hash, auth pages ignored to avoid a loop) has one implementation. While `isLoading` those pages render `null`, so a signed-in reload never flashes the form. `/reset-password/*` stays reachable signed-in because an emailed reset link must work. On sign-in, `setUser` makes `App` redirect before `LoginPage`'s own `navigate` runs (to the same place, harmlessly, after unmount). Unknown paths render `NotFoundPage` (keeping the typed URL) instead of the old silent redirect to `/movies`; signed-out users go through `/login` first and land on it after.
- **Local dates: device "today", per-entry history** — Every "which day" decision used to be UTC (stats `.date()`, Calendar `toISOString()`, Watched page splitting the ISO string, the notifications server date), so anything near midnight landed on the wrong day outside UTC. A user can have devices in different zones, so a per-account `Profile` time zone was rejected: it goes stale when travelling and needs a migration plus a UI. Bucketing everything client-side was rejected because notifications' unread state is server logic. Instead the device sends its IANA zone as `X-Timezone` on every authenticated call, and it decides "today" for that request. Each `WatchedEntry` stores the zone it was logged in (`watched_tz`), so a past watch keeps its day on every device. Bad or missing zones fall back to UTC, so older clients see the old behaviour. Imported rows keep only their own zone, never the importer's: a CSV row's original zone is unknown, and blank is the honest value. The Watched page labels a date when the logged zone's *offset* differs from the device's. Offsets rather than names, because aliases (`Asia/Calcutta`, which Chromium reports, vs `Asia/Kolkata`) and same-offset zones mean the same day. The label uses a fixed `en-US` short name (so India shows `GMT+5:30`, not `IST`). The notifications `release_date > last_seen_date` rule was right all along: a release dated today was visible at the last check. Only whose "today" it used was wrong. (Since `follow-crew-credits`, unread is "not in the last mark-seen's set" instead; the date rule remains only for checkpoints from before.) `tzdata` is a direct dependency, because Linux images may lack a system zoneinfo database.
- **Card links (`CardLink`)** — Cards that open a page were `onClick` `div`s/`Card`s: no Tab stop, no `href`, no new tab. `CardLink` wraps them in a real router `<Link>`. `role="button"` + `onKeyDown` was rejected: these navigate, so "link" is the right role, and a button gets no URL preview, context menu or Ctrl-click. Converting callers to a static `to` + `state` was rejected too, because state computed at render time goes stale (`scrollY`, `stashReturnState()` must be read at click time). So `CardLink` keeps `to` as the href and, given `onNavigate`, calls it on a plain click or Enter instead of following the link. Modifier and middle clicks still fall through to the native href. Cards with their own buttons link only their poster (a button nested inside a link is invalid HTML and confusing to screen readers). The focus outline uses `:focus-visible` with per-theme colours: brand gold on dark, a darker `#8a6d00` on light, because `#f5c518` falls under 3:1 contrast on light backgrounds.
- **Layout** — `App.tsx` uses a plain flex `div.app-shell`: `<Sidebar>` (desktop) + `<main>` + `<BottomNav>` (mobile). No Ant Design Layout wrapper.
- **State** — `AppContext` for global UI state; `AuthContext` for auth; `ListsContext` for lists. Ephemeral page state (loading, pagination) stays local to each page component.
- **Scroll restoration** — HomePage, AnimePage, and PeoplePage encode `scrollY` and `loadedPages` in `navigate()` state when clicking into a detail or person page; the shared `usePaginatedFetch` hook (`src/hooks/usePaginatedFetch.ts`) handles fetch-page-1/loadMore/restore-on-return for all three, replacing what used to be ~90% duplicated per-page logic. On back-navigation it re-fetches the required pages in parallel and restores scroll position via `useLayoutEffect`. `SearchPage`'s tab-based search (`usePaginatedSearch`) has different restore mechanics (per-tab `sessionStorage` cache keyed by query, since its tabs mount/unmount independently) and is intentionally not merged into the shared hook. WatchlistPage persists search query, sort key, and the type/watched-status filters in `sessionStorage`, and restores its scroll position only on a return from a title it opened: it stashes `{ scrollY, isReturn }` into its own history entry (`stashReturnState`) and passes `scrollY` to the detail page, whose Back echoes it with `isReturn`. A sessionStorage scroll key applied to every later visit, and `useNavigationType()` can't tell a return apart, because `App.tsx` passes `location` to `<Routes>`, which makes React Router report every in-route navigation as POP; WatchedPage persists search/sort/type filters the same way (minus scroll position). RecommendationsPage persists its search and type filter (`foryou_search`/`foryou_type_filter`; it has no sort control). ListsPage persists its search and sort through `useLibraryFilters` (`keyPrefix: "lists"`). All of these survive full navigation away and back.
- **API error normalization** — `src/utils/apiError.ts` exports `getApiError(error)` which extracts a human-readable string from axios errors, handling DRF's `detail`, `non_field_errors`, and field-level error shapes. Used consistently across catch blocks (rating save, CSV import, list/watched actions) so failures surface a real message instead of a generic or silently-swallowed one.
- **Ratings** — Validated 0.5–10 on both `RatingEntry.user_rating` (model `MinValueValidator`/`MaxValueValidator`) and the serializer field, matching TMDB's own rating scale.
- **CI/CD** — `.github/workflows/ci.yml` runs three jobs on every push/PR to main: frontend (Jest + build), backend (`ruff check` + pytest against a live Postgres service container), and `e2e-python` (pytest-playwright against the React dev server, fully network-mocked).
- **Routing** — React Router v6. Every movie, show, and person has its own URL.
- **TypeScript** — Strict mode. All TMDB response shapes typed in `src/types/tmdb.ts`.
- **UI** — Ant Design 5 with `ConfigProvider`. Cinema-dark uses `#0d0f1a` background and `#f5c518` gold accent. Cards use `rgba` glassmorphism (`.glass-card`, `.glass-sidebar`).
- **Error boundaries** — Root, per-route, and video overlay placements.
- **Typography** — `src/constants/typography.ts` exports `FONT_SIZE.caption/body/emphasis/display`; every inline `fontSize` in the app sources from this scale instead of a hardcoded number (icon-scaling `fontSize` props on antd icons are the one exception). Heading sizes are set once via antd theme tokens in `src/theme/antdTheme.ts`.
- **Light theme is custom-designed, not stock antd gray** — `lightThemeConfig` (`antdTheme.ts`) previously only overrode 3 background tokens and fell back to antd's defaults for text/border/elevated-surface colors, so it looked bland next to dark mode's bespoke "cinema-dark" palette. Now carries the same full token set dark mode has (`colorText`, `colorTextSecondary`, `colorBorder`, `colorBorderSecondary`, `colorBgElevated`, plus `Table`/`Drawer` overrides) — a warm paper/cream palette (`#f8f3e8` base) sharing the same gold `#f5c518` accent as dark mode. `App.css`'s theme-scoped rules (`.app-content` gradient, `.glass-sidebar`/`.glass-overlay-card`/`.app-bottom-nav`, `::-webkit-scrollbar-*`) got light-mode equivalents to match — the scrollbar in particular was previously unscoped entirely and stayed dark-navy even on a white page.
- **No-poster fallback is a DOM element, not an image** — `PosterPlaceholder.tsx` renders a plain `<div>No Image</div>` styled to match whatever poster-card class it's given, replacing a prior `NO_IMAGE` inline SVG data-URI. The SVG version baked its "No Image" text into the image itself with a hardcoded generic `font-family`, which could never actually render in the app's Poppins font — an `<img src="data:image/svg+xml,...">` is an opaque replaced element with no access to the page's `@font-face`/loaded fonts, so changing the font-family string inside the SVG has no visible effect. A real DOM node sidesteps the problem entirely by inheriting Poppins the same way every other piece of text on the page does.
- **Date formatting** — `src/utils/formatDate.ts` (`formatDateDMY`) renders dates as `dd-mm-yyyy` regardless of the viewer's locale, used anywhere a date is shown to the user (Watched, Lists, Movie/TV Detail).
- **Info tooltips** — `src/components/InfoTooltip.tsx` wraps antd `Tooltip` + `InfoCircleOutlined` into one reusable `<InfoTooltip title="..." />`.
- **Movie/TV detail parity** — `MovieDetails.tsx` and `TVShowDetails.tsx` share `SectionHeader`, `WatchProviders`, `MediaCardGrid`, and `ReviewsSection` (all in `src/components/`) instead of each carrying its own copy, and render sections in the same order (Where to Watch → Cast → Recommendations → Similar → Trailers → Images → Reviews, with TV's Episode Guide inserted after Cast). Both load videos and reviews in their one appended detail request (`fetchMovieDetails`/`fetchTVDetails` with `append_to_response`) and render Trailers and Reviews sections from it; TV reviews were movie-only before.
- **Spoiler shield leaves content out, and waits for progress** (`spoiler-shield`) — `EpisodeGuide.tsx` hides episodes after the user's `EpisodeProgress` (`isEpisodeHidden` in `src/utils/spoilerShield.ts`; the tracked episode counts as reached, specials are never hidden) by not rendering their title, overview or still at all, rather than blurring them: blurred text stays in the accessibility tree, and a blurred `<img>` is still downloaded. The guide shows no episode until the progress request settles, since showing episodes first and hiding them after would flash the spoilers. It still requests the first regular season on mount, alongside the progress request (the tmdb client's `sharedGet` joins the real load to it), so most users don't wait an extra round trip; a tracked user then opens on their own season. Only the first load gates the list: a later progress reload (Retry) leaves it in place. `useEpisodeProgress` derives `loading` from the key of the last settled load (`showId:retryToken`, like the library hooks' session generation), so it is true from the first render for a show, because a child's effects run before the parent's, so the guide would otherwise read "request not started" as "no progress". A failed progress load shows the guide unshielded with a note, so a side request can't block it. The first season is chosen once, ref-guarded, so a later Next Episode never moves the season being viewed. The on/off switch is a device preference (`cinedb_spoiler_shield`), like the theme.
- **Library card parity** — `WatchlistPage.tsx`, `WatchedPage.tsx`, and `ListsPage.tsx` share `LibraryItemCard.tsx` for their item grids instead of three near-duplicate `Card`/`Card.Meta` blocks; `PeoplePage.tsx`, `SearchPage.tsx`'s People tab, and `FollowingPage.tsx` share `PersonCard.tsx` the same way. `LibraryItemCard.tsx`'s outer `motion.div` carries `height: "100%"` so every card in a grid row matches the tallest sibling's height regardless of its own content length (review text, rating tag, etc.) — without it, the antd `Col` stretches (default flex behavior) but the visible card box inside doesn't fill that space.
- **Mark-watched capture** — `MarkWatchedModal.tsx` is the single place that turns a "mark watched" click into a `WatchedEntry` with `runtime_minutes`/`platform` filled in: given only `mediaId`/`mediaType`, it fetches the title's detail itself through the same appended `fetchMovieDetails`/`fetchTVDetails` call the detail page makes (one request, usually a shared or cached hit), reading runtime and `watch/providers` (platform options) from it, so a malformed providers part can't cost the runtime, so every call site — `MovieDetails.tsx`, `TVShowDetails.tsx`, `Movie.tsx`, `TVShowCard.tsx`, `RecommendationsPage.tsx`'s `RecCard`, `SearchPage.tsx`'s Movie/TV tabs, `WatchlistPage.tsx` — only needs those two IDs, no prop-drilling of detail data. Un-marking watched bypasses the modal entirely (instant toggle, same as before). The runtime is editable and prefilled by `prefillRuntime()`: a TV watch is the whole series (episodes × episode length, falling back to the latest episode's runtime because newer shows often list no `episode_run_time`). Per-episode tracking was rejected: a watch is one entry, and the user can correct the estimate. Entries created before this existed (or via CSV bulk-import) have `runtime_minutes = null` and don't count toward "Hours Watched" — a known, accepted gap rather than a bug.
- **Single source of truth for "watched"** — `WatchlistEntry` has no `watched` column; `WatchlistPage.tsx`'s watched status, filter, and card display all read live from the shared `WatchedContext` (`isWatched(id, type)`) instead of a second, independently-toggled boolean. Previously the two could disagree — marking something watched from `SearchPage.tsx` (or any other page) wrote only to the separate `WatchedEntry` table, leaving the Watchlist page's own `watched` column stale until toggled there directly.
- **List rename** — `PATCH /api/lists/<id>/` (added alongside the existing `DELETE`) accepts a partial `{name, description}` body via `UserListSerializer(..., partial=True)`; no new endpoint path, just a second method on the existing `lists_detail` view.
- **Release Calendar window** — Reverted from a 60-day to a 7-day lookahead. The 60-day window was cosmetic: `fetchAllPages` caps each of the movie/TV discover queries at 3 pages (~60 items) sorted by release-date ascending, so on any day with meaningful release volume the cap exhausts within the first week regardless of the window's stated length. `fix-browse-results` replaced the date-ascending sort with `popularity.desc` over the same window and cap: measured on 2026-10-15, 815 movies fell in a week and all 60 fetched were dated day one, while the 60 most popular span every day. Items are deduped by `type-id` before grouping (TMDB's paginated results can repeat an item across adjacent pages under concurrent fetch, which previously caused a React key-collision warning and rendering the same title twice).
- **Four honest load states** (`surface-failures`) — Every load ends as loading, error-with-retry, empty, or content. The library hooks (`useWatched`/`useWatchlist`/`useRatings`/`useLists`) start `isLoading` at `isAuthenticated` (not `false`), so the first frame before the effect runs reads as "loading" instead of "loaded and empty", and they expose `error` instead of letting a failed load fall through as an unhandled rejection that looked exactly like an empty library. A failed *reload* keeps the items already shown. `reload()` still rethrows, so explicit callers (CSV imports) keep their own error toasts. Pages branch skeleton → `LoadError` → empty CTA → content, and only block on loading while there's nothing to show yet, so a background reload never unmounts an open modal.
- **One shared `LoadError` component** — `src/components/LoadError.tsx` (antd `Result`, `error`/`notFound` variants, optional `onRetry`) replaces each page's own error `Result` and its `window.location.reload()` Retry button. Retry now refetches in place, bumping a `reloadKey` in the fetch effect's deps.
- **Detail pages degrade per section** — Movie/TV/Person pages use `Promise.allSettled`. Only the main details call is essential: a 404 there renders not-found, and any other failure renders `LoadError`. A failed reviews/similar/providers/credits/images call only leaves that section empty (`settledData()`/`isNotFound()` in `src/utils/settled.ts`). With `Promise.all`, one flaky optional call used to error the whole page.
- **In-flight dedupe in the hooks, not at the buttons** — `createInflight()` (`src/utils/inflight.ts`) gives each mutation hook a per-item slot: a second `run(key, …)` while the first is pending returns the *same* promise, so a double-click sends one request and both callers settle with the same outcome. Watchlist/watched share one slot per title across add/remove/toggle, so a remove fired while the add is pending can't race it. `toggle` wraps the unguarded inner `addRaw`/`removeRaw`, never the guarded `add`/`remove`: the guarded ones would await toggle's own pending promise and deadlock. The guard sits in the hooks because there are ~25 toggle call sites. `useToast` passes `key: msg`, so the deduped caller's identical toast replaces the first one instead of stacking.
- **`usePaginatedFetch` generations** — A `generationRef` is bumped on every real (post-StrictMode-guard) page-1 load. Page-1 and `loadMore` responses that started under an older generation are dropped, so a slow "load more" from the previous query can't append to the new one. Items are cleared only on the plain page-1 path, never on either restore path. The guard now also keys on a `retryToken`, so `retry()` re-runs page 1 with an unchanged `fetchPage`. A `loadMore` failure toasts from inside the hook, which is why `useToast` is memoized: `loadMore` needs a stable identity for `useInfiniteScroll`.
- **Rating dialog owns its close** — `RatingModal` awaits `onSave`/`onRemove` and closes only on success. Callers show their own error toast and then **rethrow**, which is how the dialog knows to stay open with the stars and review intact. It also offers "Remove rating" for an existing rating; the DELETE endpoint and `useRatings.remove` existed before, but no UI reached them.
- **Followed people and notifications are providers** — `FollowedPeopleProvider` (`src/context/FollowedPeopleContext.tsx`) replaces one `useFollowedPeople()` hook instance per `PersonCard` (N fetches, N unshared copies, so an unfollow on a card never reached FollowingPage). Its fetch is **lazy**: it starts when the first `useFollowedPeople()` consumer mounts. An eager global fetch put an unmocked `/api/followed-people/` call on every authenticated e2e page, and it 401→login-redirected tests intermittently. `NotificationsProvider` (`src/hooks/useNotifications.ts`) gives the Sidebar and BottomNav bells one poller. The bell snapshots which items were unread when it opens, renders them bold from that snapshot, and calls `markSeen()` on close instead of open. Marking seen on open zeroed `isUnread` in the same render batch, so no one ever saw a bold item.
- **Browse filter scope** — Applied browse filters belong to one media type. `App.tsx` derives a `filterScope` (`movie`/`tv`/`anime-tv`/`anime-movies`, `null` off browse pages via `browseScope()` in `src/utils/browseFilters.ts`). When a non-null scope differs from the last one, the applied filters and sort reset **during render**, not in an effect. Child effects run before the parent's, so an effect-based reset let the newly mounted page fetch once with the previous scope's filters. A detail page has scope `null`, so Movies → detail → Movies keeps its filters. `FilterPanel` is keyed by the scope and seeds its draft from the applied values, so the panel matches the grid after that round trip. Genres live in `UIContext` (a parent provider, which can't be set during this render), so they are cleared in an effect. Pages also pass the selected ids through `genresFor()`, which drops ids that don't exist for that media type: TMDB's movie and TV genre ids don't map one-to-one (`movieGenres`/`tvGenres` in `src/constants/genres.ts`). `hasActiveFilters()` is the single "use discover instead of the category" check. It ignores `includeAdult`, which used to make every Apply count as filtered, and it counts a selected genre, because category endpoints silently ignore `with_genres`.
- **Browser Back restores browse pages** — The in-app Back button navigates with `isReturn: true` in state. Browser Back used to pop the browse page's original history entry (no `isReturn`), so it reset. Before leaving for a detail page, Home/Anime (cards, hero banner, Recently Watched strip) call `stashReturnState()` (`src/utils/browseReturnState.ts`), which merges the restore info into the current entry's `history.state.usr` with a raw `replaceState`. That's the field React Router v6 rebuilds `location.state` from on `popstate`. A replace-`navigate` would do the same, but it re-renders the browse page on its way out. Raw `replaceState` emits no event, so nothing renders. This relies on the router's internal `usr` field: a Jest test pins the shape, and `test_browser_back_restores_category` fails if a router upgrade renames it. Search tabs track their own scroll only while active (each visited tab stays mounted, so saving `window.scrollY` at unmount gave every tab the active tab's position), and restore with a few-frame retry because a freshly shown pane can lay out after the first `scrollTo`.
- **Browse grids hide watched titles** (`fix-detail-and-nav`) — Movies/TV/Anime leave out anything in `WatchedContext` (`visibleItems` in `HomePage`/`AnimePage`), so a card marked watched from the grid leaves it at once. That's intended: browse is for finding something new, and the Watched page holds the rest. A search term turns the filter off, and the Search page never applies it, so a watched title stays findable and shows its watched state. The decision was settled 2026-10-12 after the audit asked whether the vanishing card was a bug.
- **Watched-title metadata backfill** — Genres, original language and release year on `WatchedEntry` are filled by one module, `backend/userdata/metadata_backfill.py`. `/stats` calls `request_backfill(user_id)`: fire-and-forget, at most one thread per user, using the same in-process coalescing model as `recommendations.request_refresh`. `_compute_personalized` calls `backfill_entries()` synchronously because clustering needs genres. Before this, genres were only filled inside personalized recommendations (skipped below 3 watched titles), so a small library never showed Top Genres. `/stats` also started a fresh 20-worker thread on every request and retried failed rows forever. TMDB fetches run in a 5-worker pool, but **DB writes stay on the calling thread**: pool workers that touch the DB each open a connection that is never closed. A 404 or a title with no genres is "settled": `WatchedEntry.metadata_settled` is set (a 404 also stores the `??`/`-1` sentinels), so no worker or restart fetches it again. It used to be an in-process set, which every gunicorn worker and every restart refetched. A transient failure backs off for an hour; that backoff map stays in memory and is capped at 10,000 entries. One run fetches at most 100 titles (newest watches first), so a bulk import of 500 unknown ids can't fan out into 500 TMDB calls on the server's key; later stats visits fill the rest.
- **Upstream failures never overwrite data** — `_ensure_cached` used to write empty genres/cast on a TMDB failure. That replaced good data and kept the title out of For You for the full 7-day cache window. It now returns the existing (even stale) row, or `None` and stores nothing. Same rule for the per-person credits cache behind notifications (`tmdb:person_credits:<id>`, 6h, shared by every follower, trimmed to the fields read): a failed fetch is never cached. Notifications now cover every followed person (they used to cover only the 10 most recent), and the cache is what keeps that affordable. Cache reads and writes happen on the request thread for the same reason as above: the production cache is DB-backed. The same split applies to the recommendations refresh: `_fill_media_cache` runs only `_fetch_media_details` (HTTP) in its 10-worker pool, and `_store_media_cache` upserts on the calling thread. The refresh thread's entry point (`_refresh_thread`) closes its own connection when it ends, like `metadata_backfill._run_backfill`. It's the thread target rather than `_refresh_cache` itself, because tests call `_refresh_cache` on the main thread, where closing the connection would break the test transaction.
- **Recommendations survive a TMDB outage** — Each section builder turns a TMDB failure into an empty section, so a refresh during an outage used to replace good recommendations with empty ones for the 12h TTL. Every except-branch that drops content now marks a shared `FetchHealth` (a lock + `failed` flag passed into both compute functions). `save_recommendations()` (used by the refresh thread and `compute_recommendations`) keeps the stored row untouched when the compute failed *and* the new result has fewer non-empty sections, or none. With no stored row it writes nothing, so the endpoints keep answering `pending` and the next request retries. Raising on any failure was rejected: one flaky title would block every refresh. Comparing section counts only blocks a refresh that actually lost content, and a clean compute always writes, even if it has fewer sections.
- **Refresh status across processes** — `_computing_users` exists only in one gunicorn worker, so a poll landing on a worker that wasn't refreshing answered `ready`, and the page stopped polling while another worker was still computing. `UserRecommendationCache.refreshing_since` is stamped by `request_refresh` (calling thread, one `UPDATE`; a no-op with no row, when the endpoints answer `pending` anyway) and cleared by `_finish_refresh` when no follow-up run is queued. The clear only touches the exact stamp this process wrote (`_own_stamp`; see "Each refresh clears only its own stamp" below), so a refresh started meanwhile on another process keeps its own. Both endpoints report `pending` while the user is in `_computing_users` *or* the stamp is within `REFRESH_STATUS_WINDOW` (10 minutes, far above a normal refresh), so a killed process's stamp expires on its own. Client-side polling until `computed_at` changes was rejected: the client can't know a refresh started on another worker.
- **Notifications poll budget** — With a cold credits cache, one notifications poll used to fetch every followed person (5 at a time, 10s timeout each) and cache them only at the end, so ~500 follows ran past gunicorn's 30s `--timeout`: the worker was killed, nothing was cached, and every later poll died the same way. `_fetch_followed_people_credits` now takes `max_fetch` and `budget_seconds`. Notifications passes `NOTIFICATIONS_MAX_FETCH=40` and `NOTIFICATIONS_BUDGET_SECONDS=15`. Uncached people are taken in followed order and each is cached on the request thread as its fetch completes (`as_completed(timeout=…)`), so the next poll's first 40 uncached people are new ones: 500 cold follows are covered in 13 polls (~39 min at the 3-minute poll interval). At the deadline the pool is shut down with `wait=False, cancel_futures=True`; at most 5 already-running fetches finish in the background and touch no DB or cache. `test_notifications` pins the budget at ≤ gunicorn's `--timeout` − 10, parsed from `docker-entrypoint.sh` like `test_tmdb_proxy`'s pin. Followed-people recommendations (`limit=10`) got the same deadline later (`fix-upstream-resilience`). A person TMDB 404s is cached as no credits, so it no longer costs one of the 40 slots every poll.
- **Avatar versioning and cleanup** — `avatar_upload_path` names each upload `avatars/user_<id>_<ms>.<ext>`, so a replaced photo gets a URL no cache has seen; a fixed `user_<id>.<ext>` meant a same-format re-upload kept its URL and browsers kept showing the old photo. The upload view stores the new file and saves the row inside `atomic()`, and deletes the old file `on_commit`; on any failure it deletes the newly written file and re-raises, so the row and the old photo stay. Removing a photo also deletes on commit. A `post_delete` receiver on `Profile` deletes the file on commit too, which covers account deletion: the old guessable URL used to keep serving a deleted user's photo. Existing `user_<id>.<ext>` files weren't renamed; they keep working until replaced.
- **Entry page revalidated, missing chunks 404** — `nginx.conf`'s `location /` used `try_files $uri $uri/ /index.html` for everything, static assets included. After a redeploy removed the old hashed chunks, a tab holding the old `index.html` requested `/static/js/main.<old>.js` and got `index.html` back with status 200, which fails as JavaScript and leaves a blank page. Now `location /static/` is `try_files $uri =404`, and `index.html` is sent with `Cache-Control: no-cache` (revalidate every load) via `map $uri $entry_cache_control` plus a server-level `add_header`. After the SPA fallback `$uri` is `/index.html`, so every route's entry page gets it, and the empty `default` means other responses send no header (the same trick as HSTS). Neither location declares its own `add_header`, because one would drop every inherited security header for that location. `test_nginx_conf.py` checks that statically, since Docker isn't available everywhere. Long-lived caching of hashed assets was left out of scope (added later, see the next bullet).
- **Static assets compressed and cached by hash, the API left alone (`harden-ci-2`)** — The 1.5 MB main bundle went uncompressed, and every reload revalidated chunks whose names already change with their content. `/static/` holds only CRA's content-hashed files, so `map $uri $static_cache_control` gives them `public, max-age=31536000, immutable`. Unhashed `public/` files (favicon, manifest, logos) are at the root and get nothing. Its `add_header` leaves off `always`: nginx then adds it only to 2xx/3xx, so the 404 for a missing old chunk is never cached for a year. The entry page's `always` header is untouched, and since at most one of the two maps is non-empty per URI, a response carries one `Cache-Control`. `gzip` is server-level (so a future static location inherits it) and turned back off in `/api/` and `/media/`. API JSON carries tokens next to request-influenced content, the BREACH pattern for compression over TLS, and media is already-compressed images. Compressing the API would be its own decision (e.g. Django's `GZipMiddleware` on chosen views), not a side effect of a static-asset fix. `gzip_types` lists both `application/javascript` and `text/javascript`, because which one `mime.types` maps `.js` to has changed between nginx versions. CI's `docker` job checks all of this against the real built image (`.github/scripts/smoke-frontend.sh`). It boots nginx with `--add-host backend:127.0.0.1`, because nginx resolves `proxy_pass` hosts at startup and won't start without that name.
- **TMDB client token policy** — `tmdb_proxy` is `AllowAny`, so the client used to send no token, and `TmdbProxyThrottle` (a `UserRateThrottle`) fell back to the IP: users behind one NAT shared one 120/min bucket. `src/api/tmdb.ts` now attaches the stored access token. Under DRF's JWT authentication an expired or invalid token is a 401 *even on an AllowAny view*, so a 401 is retried once without the token (`_noAuthRetry`, which the request interceptor also checks so it doesn't re-add it). It never logs out and never refreshes: refresh stays only in `userApi`'s interceptor, and the next `userApi` call refreshes the token anyway. Sending the token made path traversal worse, so route ids were validated first: `useValidId()` accepts only `^[1-9]\d{0,9}$` ≤ INT32_MAX. React Router decodes params, and `/movie/..%2F..%2Fwatchlist` used to request `/api/watchlist?append_to_response=…` through the proxy path builder (reproduced in `e2e/route-ids.spec.ts` with the check removed).
- **CSV formula neutralization** — Exported titles, list names and reviews are user- or TMDB-controlled, and a cell starting with `=` `+` `-` `@` tab or CR runs as a formula in Excel/Sheets. `export.ts`'s `escape()` prefixes `'` (shown as text) to such cells *and* to cells already starting with `'`. `parseCSV` strips one `'` only when it's followed by one of those characters or another `'`. That keeps the pair reversible (`''x` → `'x`), so backups round-trip exactly. Backups from before the change import unchanged: a real leading apostrophe (`'Salem's Lot`) is followed by a letter and kept. The one lossy case, an old file whose cell literally starts `'=`, was accepted. Stripping on import was chosen over leaving the prefix in the data, which would corrupt every re-imported title.
- **Third-party URLs** — TMDB person homepages are community-edited, so `PersonPage` renders one as a link only through `safeHttpUrl()` (`src/utils/safeUrl.ts`: `new URL()` parse, `http:`/`https:` only), and otherwise as plain text. The CSP blocks `javascript:` navigation in Docker, but not in dev or any deploy without nginx's headers.
- **`usePaginatedFetch` replay guard arms at load start** — StrictMode (dev only) runs the mount effect, its cleanup and the effect again, synchronously. The guard used to record the consumed `fetchPage`/`retryToken` in the load's `finally`, after the fetch settled, which was too late: the replay found the guard empty, and since the cleanup had cancelled the first pass, it started a full second load. So under `npm run dev` every first load and Back-restore requested each page twice. `inflightRef` is now set before `load()` starts. A replay with the same pair revives the in-flight load (resets `ctl.cancelled`) and returns a cleanup that cancels it again, so a real unmount still stops it. A replay after completion is a no-op as before. Production never replays, so its behavior is unchanged. Note when verifying with Playwright: `page.on("request")` can miss requests fired right after `go_back()`, so count against Django's request log instead.
- **Strict e2e catch-all** — Both e2e suites register `**/api/**` before any other route (Playwright matches last-registered-first, so every specific mock wins). An unmocked app API call is recorded, answered with 501, and fails the test at teardown with its URL. Before this, an unmocked call fell through to a missing backend: a 401 started the refresh interceptor's `/login` redirect, and tests failed with a misleading "element not found", or passed against a different page than intended. Unmocked TMDB proxy calls get an empty page instead, because they're decorative on most pages (hero, providers) and making them strict would mean mocking every one. Mocks for list endpoints use `paginated()`, the real DRF shape. `fetchAllPages()` also accepts a bare array, so `[]` mocks had been passing on a response shape production never sends.
- **Theme-dependent colors come from tokens, not literals** — `StatsPage` used to draw labels, legends, empty heatmap cells and both tooltips (a Recharts `content` component and a `createPortal` hover box) with `rgba(255,255,255,…)` and a fixed navy background, so light mode rendered them white-on-cream. Each subcomponent now reads `theme.useToken()` itself (`colorTextSecondary`/`colorTextTertiary` text, `colorFillTertiary` empty cell, `colorBgElevated`/`colorBorderSecondary`/`colorText` tooltips) instead of threading a token through props. Scoped CSS (`body.dark-theme .x`) wasn't an option: the styles live inside Recharts render props and a portal outside the page tree. The heatmap's green scale is fixed on purpose (GitHub's contribution palette reads on both backgrounds). The token values are close to, but not identical to, the old dark literals, so dark mode shifts slightly (most visibly the tooltip background).
- **Stats rounds half up (`fix-stats-math`)** — Python's `round()` is banker's rounding, so 6.5 went into bucket 6 but 7.5 into 8, and the bucket for 2 held 1.5 and 2.5 while 3 held only 3.0. Averages had the same problem: a 7.25 average showed as 7.2. `stats_views.py`'s `round_half_up()` rounds every average (`avgUserRating`, `avgTmdbRating`, per-genre `avgRating`) through `Decimal(str(x)).quantize(..., ROUND_HALF_UP)`, and the buckets use the same rule, clamped to 1–10, so each bucket covers exactly two half-star values. Going through `str` keeps a float like 7.2499999 from a sum/len from drifting. `math.floor(x + 0.5)` was rejected, because the float addition itself can misround a value just below .5. In the same change, monthly activity became contiguous (first watch month through the device's current month, zeros included), and the average TMDB rating leaves out stored `0` scores (unreleased titles, CSV rows with no score) and is `null` when no title has a score.
- **For You retries in place** — `RecommendationsPage`'s fetch/poll effect is gated by a `hasFetched` ref (so a cached complete snapshot skips the fetch) and keyed on `[isDataLoading, watchedList.length]`. Retry used to be `window.location.reload()`, which threw away every other page's in-memory state. A `retryToken` in the effect deps now re-runs it: `retry()` clears `hasFetched`, resets `fetchError`, sets `loading` and bumps the token. Same pattern as `usePaginatedFetch`'s `retryToken`. `ErrorBoundary` keeps its reload, since a crashed render tree has nothing to refetch in place.
- **One source per color rule** — `ratingColor()`/`avatarColor()` live in `src/utils/colors.ts` (there were 5 and 2 identical copies), with `RATING_WARN`/`RATING_BAD` beside `RATING_GOLD`/`WATCHED_GREEN` in `src/constants/ui.ts`. `AVATAR_COLORS` is `as const` so the modulo index's fallback is a `string`, not `string | undefined`, under `noUncheckedIndexedAccess`. `App.css`'s scrollbar-hover gold stays a literal because plain CSS can't import a TS constant.
- **Notification popup placement is per host** — `NotificationBell` lives in two places, and antd measures popup overflow against the popup container, not the viewport. Because of the CLAUDE.md sticky-sidebar rule, that container is the sidebar or the bottom nav, never `document.body`. With no `placement`, the popup opened `bottomLeft` and landed 85–290px off the left edge at every breakpoint. Each host now passes its own placement. `Sidebar` uses `topLeft` with `autoAdjustOverflow={false}`, because antd otherwise flips it right-aligned inside the 64px rail, and up-and-right from the bottom-left corner always fits. `BottomNav` uses `top`, which fits at 320px. `e2e/responsive.spec.ts` measures the popup box at 7 viewport/page combinations and checks it stays anchored on scroll.
- **Rail footer is a 2-column icon grid** — At 64px (tablet, or desktop collapsed), the footer's bell/theme/collapse row didn't fit, so it overflowed left and clipped the bell. The old rail rule's `padding: 8px 4px` was also silently losing to the footer's inline padding. Stacking the icons vertically cost 46px on browse pages at 768px tall, and the sidebar is already flush there. So in rail modes `.sidebar-footer` becomes a `repeat(2, 30px)` grid, and `.sidebar-footer-icons` uses `display: contents`, so the browse-page Filters button shares the grid: [Filters, Bell] [Theme, Toggle], the same 2 rows as before. The buttons are 30px, not antd's 32px, because the rail's 1px border leaves 63px. The footer's layout lives in `App.css` classes, not inline styles, so the rail rules can override it.
- **App icons** — `public/icon.svg` is the source for `favicon.ico` (16/24/32/64 frames), `logo192.png` and `logo512.png`: the sidebar's compact gold "C" (Poppins 700, outlined to a path so no font is needed) on the manifest `theme_color`. To regenerate, render the SVG at each size with Playwright (`page.screenshot(omit_background=True)`; change only the root `<svg>`'s width/height, since the `<rect>` carries the same attributes), then build the ICO with Pillow (`save(format="ICO", sizes=..., append_images=...)`) from the natively rendered small frames rather than downscaling the 512.
- **TMDB connect is bound to the user who started it** — `tmdb_request_token` stores the token it issues under `tmdb_req_token:<user_id>` in the shared cache (60 minutes, TMDB's own token lifetime), and `tmdb_create_session` accepts only that token, once. Before this, any signed-in user could be sent a `/tmdb-callback?request_token=<T>&approved=true` link for a token the attacker had approved in their own TMDB account, and every later rating would sync to the attacker. The token is consumed even if TMDB then fails, so a failed exchange means clicking Connect again. Reconnecting revokes the previous session first, like disconnect does. The cache (not a DB column) holds the token because it lives an hour and the cache already backs throttles across workers.
- **TMDB credentials in logs** — `RedactingFormatter` also strips `session_id=`/`request_token=` values (and `"session_id": "…"` in JSON), because `requests` puts the full URL in every `HTTPError` message. Rating sync logs only the exception type, and a user with no TMDB link logs nothing: that's the normal case, and it used to write an ERROR traceback on every rating.
- **Login failures are limited per username too** — Besides the per-IP `login` throttle, `login` counts failures per username (hashed) and returns `429` for that username once it has 20 within an hour of the first, checked before the password and the same for unknown usernames. This stops distributed guessing from many IPs. Trade-off, accepted: anyone who knows a username can keep it out of password login for up to an hour. Password reset still works and clears the count, and the limits are `LOGIN_FAILURE_LIMIT`/`LOGIN_FAILURE_WINDOW_SECONDS` in settings.
- **The login-failure counter is a table, not the cache** (`harden-account-input`) — It started as `cache.add` + `cache.incr` in `default`. In production that's `DatabaseCache`, whose inherited `incr` is a `get` then a `set` with the default 300 s timeout: every failure pushed the expiry to 5 minutes, so the "1 hour" lock lapsed 5 minutes after the 20th failure, and a parallel burst from many IPs counted as about one. `default` also culls at `MAX_ENTRIES`, which can evict counters. The tests ran under DEBUG's `LocMemCache`, whose `incr` keeps the expiry under a lock, so none of it showed. Now `LoginFailure(key, count, window_start)` is written by one `INSERT … ON CONFLICT DO UPDATE` that restarts the window only once it has passed. PostgreSQL serializes concurrent upserts on one key, so every failure counts, and the database clock is the only clock. Expired rows are deleted as new failures are recorded. Profile `current_password` checks and account deletion count toward it and are blocked by it too, so a stolen session gets the same 20/hour as a login guesser, not the 5000/day `user` bucket.
- **Reset request and confirm are separate throttle buckets** — `password_reset` (5/hour) and `password_reset_confirm` (10/hour). Sharing one meant two link requests plus three rejected passwords on the confirm form locked the user out of their own reset for the link's whole lifetime, and NAT'd users shared it.
- **Avatars are capped at 16 MP and stored at most 1024 px a side** — Pillow's own limit (~89 M px) let a few-hundred-KB single-colour PNG decode to several hundred MB, twice over with `exif_transpose`'s copy. The cap is checked from the header before decoding, and `thumbnail()` runs before the transpose. The replace takes a row lock (`select_for_update`) around reading the old file name and saving, so two uploads at once can't both delete the same old file and orphan a new one.
- **The email-change notice is sent after commit, off the request thread, with `EMAIL_TIMEOUT`** — Sent inline, a stalled SMTP server held the request until gunicorn killed it, after the change committed but before the token revoke and reissue ran, so the user got a 502 and was signed out by the password claim. `EMAIL_TIMEOUT` (10 s) also bounds the reset-mail threads.
- **Account enumeration is accepted at registration** — Register says when a username or email is already taken, so whether an account exists is visible there. That's accepted: a clear signup error is worth more here than hiding it, and usernames can't be hidden anyway. Password reset still answers the same for known and unknown emails, and sends the mail on a background thread, so response time doesn't give it away either.
- **Avatars are re-encoded** — After the format checks, the upload is decoded and saved again in its own format with `ImageOps.exif_transpose` applied, so EXIF (GPS, camera serial) is dropped and the photo stays upright. `/media/` is public, so anything embedded in a photo was readable by anyone with the URL.
- **Access logs redact one-time credentials** — `nginx.conf` logs through a `redacted` `log_format` whose request URI and referer come from `map`s that blank `/reset-password/…` and `/tmdb-callback?…`. The referer matters as much as the URI: the reset page's own API call carries the full reset link as its `Referer`. `EMAIL_BACKEND` must be set explicitly when `DEBUG` is off, so a deploy can't silently print live reset links to stdout through the console backend.
- **Text fields are capped at the serializer** — Reviews (5000) and list descriptions (200) are `TextField`s with no database limit, so one account could store 8 MB values and make every page load of its ratings or lists pull them into a sync worker. The caps live on the serializers, not the model, so no migration runs and text already stored above them still reads.
- **Dev API traffic is same-origin through CRA's proxy (`speed-up-pages`)** — The clients used to call `http://${hostname}:8000` directly. Measured on the dev machine, that cost two things on every page. First, every call was cross-origin with an `Authorization` header, so each new URL needed a CORS preflight; since TMDB calls carry the token (0.20) that meant every movie, page and filter. Second, `localhost` resolves to `::1` first while `runserver` binds IPv4 only, so each new connection waited for the IPv6 attempt to fail: 2 s from Python, ~300 ms in Chrome, which races the two. `package.json`'s `proxy` now forwards `/api` and `/media` to `http://127.0.0.1:8000`, and the client defaults are relative, the values production already sets through `REACT_APP_*`. The `proxy` field was chosen over `src/setupProxy.js` because that file must be JavaScript and the frontend is TS-only. Mapping `localhost` → `127.0.0.1` in the clients was rejected because it fixes the fallback but keeps every preflight. A dual-stack `runserver` (`[::]:8000`) was rejected because Windows defaults `IPV6_V6ONLY` on, which would break IPv4 LAN access. CRA's own server has the same IPv4-only problem when root `.env` sets `HOST=0.0.0.0`; `HOST=::` (Node listens dual-stack) avoids it. All proxied dev traffic arrives from 127.0.0.1, so anon throttles (login, register) are shared by every dev device. That's accepted for dev.
- **One TMDB request per detail page (`speed-up-pages`)** — Movie and TV pages used to fire 5–6 TMDB calls (details plus reviews, similar, providers, release dates / credits, aggregate credits, images) and render after the slowest. StrictMode doubled them in dev, and the copies queued behind Chrome's 6-connections-per-host limit. TMDB's `append_to_response` (up to 20 parts) folds them into the details call. "Degrade per section" survives as shape guards (`src/utils/appended.ts`): a missing or malformed part empties only its section, while a failed request is the main request failing, which was already essential. The TV page appends only what it renders (`aggregate_credits`, not `credits`; no content ratings). `MarkWatchedModal` keeps its own providers call: it's a user action, not a page load. Caching the separate calls instead was rejected because it still costs 5–6 round trips and throttle ticks on a first visit.
- **In-flight sharing in the TMDB client (`speed-up-pages`)** — `sharedGet` (`src/api/tmdb.ts`) shares identical GETs (same `getUri`) while they're in flight and forgets them on settle. That covers StrictMode's double mount for every fetcher at one point, instead of per-component guards like `usePaginatedFetch`'s. It shares only in-flight requests, never results, so there's no client cache to invalidate. Waiters share the same response object, which callers only read.
- **TMDB proxy cache in its own alias (`speed-up-pages`)** — `tmdb_proxy` stores `200` bodies in the `tmdb` cache alias, keyed on path + forwarded params (the client's `api_key` excluded). TTLs: lists 10 min, genre/configuration 24 h, details 6 h. Throttling runs before the view, so hits still count. It's a separate alias because culling in `default` (`DatabaseCache`, also holding throttle counters) would evict counters, and two LocMem aliases with the same (empty) `LOCATION` share one store, so the dev alias is named `tmdb-proxy`. Credential params (`session_id`, `guest_session_id`) and `account`/`authentication` paths bypass the cache. A cache backend error is a miss, never a 500. No stampede lock: concurrent misses both reach TMDB, which the client-side sharing already limits.
- **Library lists in pages of 500 (`speed-up-pages`)** — `fetchAllPages` awaits each page before the next, so a 1,300-title watched history took 13 sequential requests on every reload. `DefaultPagination` now takes `page_size` up to 500, and the watched/watchlist/ratings hooks ask for 500 (3 requests). Lists (nested items) and followed people keep 100. Parallel page fetching was left out: with 500-row pages the remaining round trips don't justify the ordering and error-handling code.
- **`CONN_MAX_AGE` only in production (`speed-up-pages`)** — A Postgres connect costs ~50 ms here. With `DEBUG` off, gunicorn's sync workers keep a connection for 60 s (`CONN_MAX_AGE` env). Under `runserver`, every request runs on a new thread, so a kept connection is never reused and is only left open; it stays 0 there. Dev pooling would need psycopg 3's pool (`OPTIONS: {"pool": True}`), a dependency swap left in backlog item 26.
- **A failed load-more page waits for Retry (`fix-upstream-resilience`)** — `loadMore`'s identity changes when `loadingMore` flips back in `finally`, so `useInfiniteScroll` re-`observe()`s the sentinel, and IntersectionObserver always reports the current intersection on `observe()`. After a failure nothing was appended, the sentinel was still in view, and the page re-requested the same page in a tight loop. While TMDB was down, each try held a gunicorn worker for the proxy's full time budget. `usePaginatedFetch` now keeps a `loadMoreError`, and `loadMore` returns early while it's set; only `retryLoadMore()` (the inline `LoadMoreError` button) tries again. The guard lives in the hook rather than in each page's `enabled`, so a page that forgets the `enabled` term still can't loop. Exponential backoff was rejected: it hides the failure and keeps spending quota during an outage. Changing the observer to skip the initial callback was rejected too, because a successful load relies on it to keep chaining pages while the sentinel stays in view.
- **A TMDB 404 is an answer, not an outage (`fix-upstream-resilience`)** — The recommendation sites (`_fetch_media_details`, `fetch_similar`, `fetch_actor_credits`) caught a 404 together with every other `RequestException` and marked `FetchHealth` failed. One deleted or merged title or actor in a user's data then marked every refresh failed. `save_recommendations` kept discarding any smaller result, `computed_at` never advanced, and every For You visit started another full recompute. The title was also refetched every run, because a failure stores nothing. `tmdb_client.is_not_found()` now splits a 404 out at every TMDB consumer. Title details store an empty `TMDBMediaCache` row for the 7-day window, similar titles and actor credits contribute no section, and a followed person is cached as `[]` credits for 6 h. The metadata backfill already did the same with `metadata_settled`. A TMDB that wrongly 404s would settle titles as empty for one cache window. That's accepted, because the entries refresh at their TTL.
- **Genre backfill failures count against a refresh (`fix-upstream-resilience`)** — `_compute_personalized` clusters on genres and calls `backfill_entries` first, which swallowed failures. A refresh during a TMDB blip then clustered genre-less titles and saved the result as good for 12 h. `backfill_entries` now returns `False` when a fetch or store failed, or when a title was skipped while in backoff from an earlier failure, and the compute marks `FetchHealth` failed. Titles left over only by the `MAX_PER_RUN` cap don't count: that's pacing, not a failure.
- **Each refresh clears only its own stamp (`fix-upstream-resilience`)** — `_finish_refresh` used to clear any `refreshing_since` no later than its own finish time. That included a stamp another gunicorn worker wrote while this run was going, so the next poll could say `ready` with the older result. `request_refresh` now records the stamp it wrote in `_own_stamp[user_id]`, and the finish clears only an exact match. A queued follow-up run writes a fresh stamp, so a chain of follow-ups can't age past `REFRESH_STATUS_WINDOW` and look killed. There's one residue, accepted: if the other process finishes first, it can't clear this process's stamp. The status then stays `pending` until this run ends, which is still honest.
- **Stats' genre lookup is bounded (`fix-upstream-resilience`)** — A cold per-process genre cache made Stats call `/genre/movie/list` and `/genre/tv/list` back to back with `timeout=10` (connect + read each), about 40 s worst case against gunicorn's 30 s. The fallback to built-in names was then cached for 24 h. Stats now passes `GENRE_LOOKUP_TIMEOUT = (3.05, 5)` and `fallback=False`, so a failure raises. It then uses `STATIC_GENRE_NAMES` and retries TMDB after 5 minutes. `test_stats_genres` pins 2 × (connect + read) ≤ `--timeout` − 10. Running the two calls in parallel under a deadline was rejected: it adds a thread pool to a lookup that's cached for a day, and the short timeout already bounds it.
- **A session generation drops responses for a signed-out account (`fix-account-edges`)** — Signing out flips `isAuthenticated`, which empties the library hooks and the notifications. A response already in flight then landed afterwards and put the old data back. If another account signed in within the same tab, it saw the previous account's bell items (which reveal whom that account follows), or kept the previous library when its own load failed. `bindSessionUser` already runs synchronously on every account change, before any re-render or new request, so it now also bumps a module `sessionGeneration`. Every hook captures `currentSessionGeneration()` before an `await` and returns early unless `isCurrentSession(gen)`. That covers success, `catch` and `finally`, so a stale `finally` can't end the new account's loading either. A same-id re-bind (a profile save) doesn't bump it. Per-effect `cancelled` flags were rejected: they don't cover `reload()` called from pages, or writes. An `AbortController` per session was rejected too: it needs a signal threaded through `fetchAllPages` and every call, an aborted write leaves the server state unknown, and a response already resolved still lands.
- **The profile dialog body is destroyed on close (`fix-account-edges`)** — The `Modal` had `destroyOnHidden`, but `Form.useForm()` lived in the always-mounted outer component, so the form store survived and rc-field-form merged it over `initialValues` on the next open: typed passwords and unsaved edits came back. Everything inside the dialog now lives in `ProfileModalBody`, which the Modal discards, so each opening starts from the saved profile. Calling `form.resetFields()` on open was rejected: the instance isn't connected while the body is destroyed (antd warns), and resetting after mount shows the old values for a frame.
- **Imported timestamps start at 1900, and old rows read in UTC (`fix-account-edges`)** — A watch time near year 1 in a zone behind UTC made `astimezone` raise `OverflowError`, so `/api/stats/` returned 500 on every request for that account. `_past_timestamp()` now rejects anything before 1900-01-01 (nobody logged a watch, rating or list add earlier, and an earlier date is a typo). `entry_local` also catches `OverflowError` and falls back to UTC, like a bad zone does, which is what repairs accounts that already hold such a row. No data migration rewrites them.
- **A forced logout keeps the return path in history state (`fix-account-edges`)** — `forceLogout()` used to assign `location.href = "/login"`, which dropped the page the user was on. It now runs `history.replaceState({ usr: { from } }, "", "/login")` and then `location.reload()`. A reload keeps `history.state` while still discarding all in-memory state, and React Router builds `location.state` from `usr`, so `LoginPage`'s existing `postLoginPath(location.state)` returns the user there. That's the same coupling as `stashReturnState`, pinned by `e2e/session-expiry.spec.ts`. A `?next=` parameter was rejected: it needs open-redirect checks and lands the path in server and proxy logs. A sessionStorage key was rejected too: `clearSession()` has just cleared sessionStorage, and a leftover key would leak into the next unrelated sign-in.
- **Export All refuses a partial library (`fix-account-edges`)** — The button exported whatever the contexts held, so a failed watched-history load gave a backup with no watched history and no warning. It now shows "Loading library…" while any part loads. If any part failed, it shows a warning naming the failed parts, with a Retry, and writes no file. The file is built in an awaited `try` with an error toast. Auto-reloading and then exporting was rejected: the values captured by the click handler are stale after `reload()`, and a silent retry hides the failure.
- **Honest states and address values** (`honest-states-a11y`) — A screen never presents a failure as an answer. For You tracks failures per recommendation group, so one failed group shows a warning beside the others, and a group still computing keeps its spinner. The person page tells a failed credits request (a non-404 rejection) apart from "TMDB has none", and its Retry refetches only the credits so the bio doesn't flash. The TMDB status in Edit Profile is three-valued plus loading (`undefined` checking, `null` failed). Query values go through `parseIntParam`/`pickKey` (`src/utils/queryParams.ts`): a number that isn't a whole number in range, or a tab that doesn't exist, means the default. The Lists page's Delete confirm is wrapped in a `stopPropagation` span because React bubbles events from antd's portaled popup through the component tree to the card's `onClick`, even though the popup isn't inside the card in the DOM.
- **Person credits cache and poll summaries** (`notifications-cache-hygiene`) — Followed people's TMDB credits live in their own cache alias, `person_credits` (a `DatabaseCache` table in production). In `default` they outnumbered the throttle counters, and past `MAX_ENTRIES` Django's cull drops the alphabetically first third of keys, which were the `throttle_…` counters. One account could force that on purpose by bulk-following arbitrary ids and polling. Sharing `tmdb` instead would let a big follow list and the proxy cull each other. Each fetch writes two keys: the full trimmed list, which followed-people recommendations read for the 10 most recent follows, and a recent summary (credits dated 32 days back to 2 days ahead of the fetch, in UTC). Polls read only the summaries, so a poll's memory grows with recent releases, not with how many credits followed people have (5,000 follows of full lists was 100–250 MB per poll). The margins cover the 30-day lookback, device zones up to a day from UTC and the 6 h cache lifetime, so a title dated tomorrow still appears when its day comes. Same-day releases: notifications compare release days with the mark-seen day, so a title dated that day used to count as read even when it first appeared later. Mark-seen now stores the same-day items the user had, from the cache alone (a poll shows only cached people, so nothing it skips was shown), and a later same-day item is unread. The client sending what it displayed was rejected: an old cached bundle would send nothing.
- **Crew credits, new work and the seen set** (`follow-crew-credits`) — A followed person's credits are their acting and every crew job (the user chose all jobs over a key-job list), one entry per title and media type, with Talk and News genre appearances dropped: "Self" on late-night shows and award broadcasts is 12–40 credits per person and isn't their work. Following a director used to produce nothing, because only `cast` was read. The per-person list behind "New from {name}" now holds only work from the last two years or dated ahead (it used to be every credit, filtered by a 6.0 rating that dropped every new title), and the cache keys carry a version (`person_new:v2:`, `person_recent:v2:`) so cast-only entries cached before the change are never read. Unread is now "not seen at the last mark-seen": mark-seen stores every item in the 30-day window (the poll's own `_window_items`, from the cache), and an item is unread when it isn't in that set, whatever its date. The old rule compared release days with the mark-seen day, so a title TMDB added late with a past date was never unread; the same-day list only patched titles dated the mark-seen day. Checkpoints from before keep the date rule until their next mark-seen, rather than showing a burst of old items as new on deploy.
- **Bounded recommendation refreshes** (`bound-rec-refresh`) — A refresh whose result `save_recommendations` refuses (TMDB failed) leaves `computed_at` unchanged, so before this every 3 s poll of the still-stale row started another full recompute on every process. A 10-minute marker in `default` now stops poll-driven triggers. It is a plain `set` with a timeout, because the no-row case needs it too (a placeholder row would read as "ready, empty"), and losing it in a cull only allows one early retry. Data changes override it. One refresh fetches at most 200 titles (missing first, then oldest cached) and keeps using stale rows it didn't refetch. Cached rows are looked up per media type in 1,000-id chunks instead of one OR'd condition per title. Background title fetches for a user (backfill and cache fill) share a 1,000-a-day budget kept in a `TmdbTitleBudget` row under `select_for_update`, not the cache (`DatabaseCache.incr` isn't atomic and resets the expiry). The per-run caps alone let an account clear, reimport fake ids and spend another run each time. A process computes at most 4 refreshes at once; the others wait on a semaphore before touching the DB. The startup warm-up skips fresh users and goes oldest first, so its 30 s go where they help.
- **Recommendation quality** (`rec-quality-fixes`) — Taste clustering uses only titles that have genres and weren't rated 4 or below. Genre-less rows were zero vectors pulling every centroid to the origin, and disliked titles still added positive weight, so ten horror films rated 1–2 could make "Your Taste: Horror". Excluding them is simpler than negative weights, which cosine scoring handles badly. A cluster whose top genres exist only on different media types (Horror on movies, Reality on TV) used to query neither type; `_genres_for` tries the pair, then each genre alone, per type, and keeps the cluster's label. Only a TMDB 404 settles a title's metadata. A genre-less answer (common before release) is rechecked after 30 days via `metadata_checked_at`. Migration `0028` unsettles legacy rows settled that way, recognised by a real language (404s are stored with `"??"`). Rated titles count as seen even if never marked watched. `save_recommendations` takes the compute's start time and, under `select_for_update`, refuses to replace a row from a compute that started later, because per-process coalescing can't stop two processes refreshing one user. Being superseded doesn't set the outage backoff.
- **Threaded workers and capped backfills** (`bound-background-load`) — Three sync gunicorn workers meant three requests waiting on a slow TMDB (proxy up to 20 s, notifications and followed-people recommendations 15 s) blocked every other request, sign-in included. `gthread` with 8 threads per worker gives 24 concurrent requests at the memory of 3 processes (numpy/sklearn load once per process); more sync workers would have cost about 3× the memory for 3× the concurrency, and `gevent` would have needed monkey-patching. Under `gthread` the `--timeout` no longer kills a slow request, so the per-endpoint TMDB budgets are the bound. The TMDB deadline pool and the proxy's connection pool grew to 16 so threads don't queue behind each other. Separately, background metadata backfills were single-flight per user only, so a burst of Stats visits started one thread, 5-worker pool and DB connection per user; they now take one of 2 per-process slots before touching the database, like recommendation refreshes (4 slots). The synchronous backfill inside a refresh doesn't take a backfill slot: it's already inside a refresh slot, and nesting the two could deadlock.
- **Region as a device preference** (`polish-library-docs`) — Where to Watch, the movie certification and Mark as Watched's platforms read TMDB's per-country `results`, and used only the `US` entry, so users elsewhere saw services they can't use. The region now defaults to the browser locale's region (`Intl.Locale(...).maximize()`, so `en-IN` and `hi` both give India and a bare `en` gives the US) and can be changed in Edit Profile, with the options from TMDB's own `/watch/providers/regions`. It's stored in `localStorage` (`cinedb_region`) and kept across sign-out like the theme, not on the account: it describes where the device is, needs no migration or API field, and a shared device in one country wants the same answer for everyone. Every reader goes through `pickRegion()`, which returns the region's entry or, failing that, the US entry flagged as a fallback, so a sparse region still shows something and the UI says whose data it is. Browse, Calendar and release dates stay global (TMDB's `region` query param), and provider deep links stay on the services' global sites, which redirect by country.
- **Watchlist pagination copies Watched's, not a shared hook** (`polish-library-docs`) — The Watchlist rendered every entry as an animated card. It now has the same page/pageSize URL params, clamp-once-loaded effect and `Pagination` block as Watched. Two callers didn't justify a `usePagedList` extraction; a third would.
- **Reduced motion, page titles and the announcer** (`a11y-motion-titles`) — Reduced motion is one `MotionConfig reducedMotion="user"` around the app plus one `prefers-reduced-motion` CSS rule that shortens every transition and animation, antd's included. Per-component checks were rejected because they miss antd and every future component; only JS-driven motion (Stats' count-up, `MarqueeTitle`) checks `useReducedMotion()` itself. Every page sets its tab title through `usePageTitle`, and `RouteAnnouncer` reads it through a small module-level subscription. After a pathname change it waits for the title to settle (about 1 s, so a detail page announces the film's name, not "Movie") and writes it to a polite live region. It deliberately doesn't move focus: the browse and library pages restore scroll on Back, and a focus move would fight that.
- **Mark as Watched holds like the rating dialog** (`a11y-motion-titles`) — `onConfirm` returns a Promise that rejects after the caller shows its error, and the modal stays open and uncloseable (no Cancel, Escape, mask or close button, a repeat confirm ignored) until it settles. Closing on click and toasting later lost the typed runtime and platform on a failed save. The pattern is `RatingModal`'s, so both dialogs behave the same.
- **Contrast pinned by computation** (`a11y-motion-titles`) — Light secondary text was 3.79:1 and light tertiary (antd-derived) about 3.3:1. Both themes now set `colorTextSecondary` and `colorTextTertiary` explicitly, chosen against the darkest background each theme puts text on (light: `#f8f3e8`), keeping the warm hue and secondary darker than tertiary. `themeContrast.test.ts` computes WCAG contrast from `antdTheme.ts` itself, so a later token or background tweak can't quietly drop below 4.5:1; the e2e readability test checks the rendered result.
