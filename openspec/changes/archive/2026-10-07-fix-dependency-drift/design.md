## Goals / Non-Goals

**Goals:**
- Dev, tests and the Docker image install the same backend dependency versions.
- Changing a version is a deliberate, reviewable edit, not a side effect of an unrelated rebuild.

**Non-Goals:**
- CI workflow changes, including adding an install-from-constraints CI job and the CI Node version. Those belong to `ci-coverage`.
- Docker hardening (non-root user, CSP/HSTS, `STATIC_ROOT`, `.dockerignore`). That belongs to `harden-docker`.
- Upgrading frontend dependencies or replacing CRA.
- Rewriting migration files.

## Decisions

### D1. Target Django 5.2 LTS, not 4.2 or 6.0
5.2 is what every test and every manual verification has run on, and it's LTS (security support until April 2028).
- **4.2** (what Docker gets today) has had no test run at all. Its support also ends in April 2026, which has already passed.
- **6.0** isn't LTS, requires Python 3.12+, and was only ever present by accident.

`requirements.txt` gets `Django==5.2.17`. Bumping to a later 5.2.x is a one-line, reviewed change.

### D2. Exact pins for direct deps plus a generated constraints file for transitive ones
- `requirements.txt` stays the human-edited list of direct dependencies, each pinned `==` to the tested version. Comments like simplejwt's `5.5.0+` note stay.
- `backend/constraints.txt` is generated, not hand-edited:
  1. Create a fresh venv from the dev env's Python 3.12.
  2. `pip install -r requirements-test.txt`.
  3. `pip freeze > constraints.txt`, with a header comment giving the regeneration command.

  It pins every transitive package (asgiref, sqlparse, PyJWT, scipy, joblib, urllib3…).
- Docker and the README install with `pip install -r requirements.txt -c constraints.txt`.

*Alternatives:*
- **pip-tools** (`requirements.in` → compiled `requirements.txt` with hashes): the best reproducibility, but it adds a tool and a build step for a small project. It's easy to move to later, because the constraints file is the same idea.
- **Exact pins on direct deps only:** leaves transitive packages (scipy, urllib3) floating, and that's where most surprise breakage comes from.

### D3. Python 3.12 in Docker; current Node LTS for the frontend build image
- `backend/Dockerfile` moves both stages to `python:3.12-slim`, matching dev's 3.12. Wheels for numpy 2.2 and scikit-learn 1.8 exist for 3.12.
- `Dockerfile.frontend` moves from `node:18-alpine` to `node:22-alpine` (the active LTS). `npm ci --legacy-peer-deps` stays. The flag is there for react-scripts 5's TypeScript peer range, not for Node.

Because Docker isn't available here, verifying the image build is a manual task.

### D4. Guard test against the wrong interpreter
Add `test_django_version_matches_requirements`: parse the `Django==X.Y.Z` line from `requirements.txt` and assert `django.VERSION[:2] == (X, Y)`. Base Anaconda's 6.0 would then fail the backend suite immediately instead of quietly writing "Generated by Django 6.0" migrations.

It checks major.minor only, so patch bumps don't need the test touched. *Alternative:* a check in `manage.py`. Rejected: it would block `manage.py` in legitimate one-off situations, and the test suite is where the mistake shows up.

### D5. Leave the migration headers alone
A migration's header is a comment. Django never reads it, and the operations are 5.2-compatible (see Context). Editing applied migration files makes diffs look like schema changes and invites mistakes. The guard test (D4) stops the mismatch happening again. *Alternative:* rewrite the headers to "5.2.17". Rejected: cosmetic, and it would rewrite history in 14 files.

Restate the reason without the Express proxy: the frontend may reach Django through different hosts (dev server, LAN IP, nginx), so it resolves the path against its own API base.

## Risks / Trade-offs

- **[The Docker image jumps from Django 4.2 to 5.2]** → It's the version all tests run on. 5.2 requires PostgreSQL 14+, and compose runs `postgres:15-alpine`, so that's fine. Rollback is reverting the requirements files.
- **[Pins go stale and miss security fixes]** → That's the point of pinning: updates become deliberate. The regeneration command is documented in the constraints header and the README. A scheduled dependency bump (Dependabot) is a CI concern, deferred to `ci-coverage`.
- **[`constraints.txt` generated on Windows could include Windows-only packages]** → Check the frozen list for platform-specific packages (e.g. `pywin32`, `colorama`) and drop them, or mark them with environment markers. They can only appear through the test tools, so the generation step reviews the diff. The Docker build (Linux) is the real check, and it's a manual task.
- **[Docker can't be built here]** → The image build and `docker compose up` smoke test are listed as manual verification for the user.

## Migration Plan

1. Land the pinned files and the Docker changes.
2. Rebuild the images (`docker compose build --no-cache`) and run `docker compose up`. The existing `docker-entrypoint.sh` migrate step is a no-op, because there are no new migrations.
3. Rollback: revert the requirements files and Dockerfiles, then rebuild.
